# 학습 노트 — 기술 & 개념 정리

이 문서는 하모니업(Harmony Up)을 만들면서 사용한 기술과 개념을, 나중에 다시 봐도 이해할 수 있게 풀어서 정리한 것이다. 단계가 끝날 때마다 이어서 추가한다. iOS 개발 경험은 있지만 DSP(디지털 신호 처리)는 이번에 처음 배운다는 전제로 쓴다.

## 1. 프로젝트 구성 — XcodeGen

**뭘 썼나**: `project.yml`이라는 텍스트 파일 하나로 `.xcodeproj`(Xcode 프로젝트 파일)를 자동 생성하는 도구.

**왜 쓰나**: `.xcodeproj`는 내부적으로 XML 비슷한 구조인데, 여러 사람이 동시에 파일을 추가/삭제하면 git 충돌이 잘 난다. `project.yml`은 사람이 읽기 쉬운 YAML이라 충돌이 거의 안 나고, "타깃에 어떤 소스 폴더가 들어가는지"가 한눈에 보인다. 새 `.swift` 파일을 추가해도 Xcode에서 일일이 타깃 멤버십을 체크할 필요 없이, 폴더에 파일만 넣고 `xcodegen generate`만 다시 돌리면 된다.

**우리 프로젝트 구조**:
```
HarmonyUp/
  project.yml              # 타깃 정의(HarmonyUp 앱, HarmonyUpTests)
  HarmonyUp/Sources/        # 앱 타깃 소스
    PitchEngine/            # 신호처리 순수 로직 (UI와 분리)
  HarmonyUp/Tests/           # 유닛 테스트
```

## 2. SwiftUI 앱 기본 구조

- `@main struct HarmonyUpApp: App`: 앱의 진입점. `App` 프로토콜을 채택한 타입에 `@main`을 붙이면 이게 실행 시작점이 된다 (예전 `AppDelegate`의 `UIApplicationMain` 역할을 대체).

- 이 프로젝트에서는 UI가 범위 밖이라 `ContentView`는 텍스트 하나만 띄우는 자리표시자로 둔다.

## 3. NoteNameConverter — Hz를 음이름으로

### MIDI 노트 번호와 로그 스케일

사람이 듣는 음높이는 주파수(Hz)에 대해 **선형이 아니라 로그(log) 관계**다. 예를 들어 A4(440Hz)에서 한 옥타브 위인 A5는 880Hz — 즉 옥타브가 하나 올라갈 때마다 주파수는 정확히 2배가 된다. 이런 특성 때문에 음악에서는 주파수 대신 "MIDI 노트 번호"라는 로그 스케일 번호를 쓴다.

공식:
```
MIDI 노트 번호 = 69 + 12 × log2(주파수 / 440)
```
- `69`는 A4의 MIDI 번호로 정해진 기준값.
- `12`를 곱하는 이유: 한 옥타브(주파수 2배) 안에 반음(semitone)이 12개 있기 때문. `log2(2) = 1`이므로 옥타브가 하나 올라가면 이 공식은 정확히 `12`만큼 증가한다.
- 결과값을 반올림하면 가장 가까운 반음(= 노트)을 찾을 수 있고, `번호 % 12`로 음이름(C, C#, D…)을, `번호 / 12 - 1`로 옥타브를 구한다.

이건 **평균율(equal temperament)** 튜닝 체계를 전제로 한다 — 한 옥타브를 12개의 반음으로 "똑같은 비율"로 나눈 현대 서양음악 표준 조율법. (참고로 국악 등 다른 음악 체계는 이 전제가 안 맞을 수 있지만, v1 스코프 밖.)

### Cent — 음정 오차의 단위

반음 하나를 다시 100등분한 단위가 **cent**다. "±10 cent 이내 정확도"라는 Phase 1 완료 조건은 반음의 1/10 이내 오차를 뜻한다. 위 공식에서 반올림 전 소수값과 반올림 후 정수값의 차이에 100을 곱하면 cent 단위 편차가 나온다 — 나중에 튜너 앱과 비교 검증할 때 이 값을 쓴다.

### 왜 nil을 반환하게 했나

주파수가 0 이하인 경우(무음/무효 입력)를 호출하는 쪽에서 억지로 필터링하게 만들지 않고, 함수 스스로 "이 입력엔 답이 없다"를 표현하도록 Optional을 리턴 타입으로 썼다. Swift에서 실패 가능한 순수 함수를 표현하는 표준적인 방법.

## 4. 코딩 컨벤션 관련 — 왜 순수 함수로 분리하나

`PitchEngine` 폴더 아래 로직들은 전부 "입력을 받아 출력을 반환"하고, 마이크나 UI 상태 같은 외부 상태를 건드리지 않는 순수 함수/타입으로 설계한다. 이렇게 하면:
- 실제 마이크 없이도 사인파 같은 가짜 입력으로 유닛 테스트가 가능하다 (XCTest).
- 나중에 pYIN으로 알고리즘을 바꾸거나 튜닝값을 조정할 때, UI나 오디오 캡처 코드를 안 건드리고 이 폴더만 수정하면 된다.

## 5. YINPitchDetector — YIN 알고리즘

### 문제: 컴퓨터는 왜 "음높이"를 바로 못 읽나

마이크로 들어온 소리는 시간에 따른 진폭 값의 배열(파형)일 뿐이다. 이 파형이 "1초에 몇 번 반복되는가(주기, period)"를 알아내면 그 역수가 기본 주파수(F0)다. YIN은 이 반복 주기를 찾는 알고리즘이다.

### 자기상관(Autocorrelation)이 하는 일

파형을 자기 자신과 비교하되, 한쪽을 tau(샘플 개수)만큼 밀어서 겹쳐본다. 밀린 정도가 실제 주기와 일치하면 두 파형이 거의 똑같아 보이고, 아니면 안 맞아떨어진다. "두 벡터가 얼마나 비슷한가"는 벡터 내적(dot product)으로 잴 수 있다 — 내적이 크면 비슷한 방향(비슷한 파형), 작으면 다른 방향. 이 프로젝트에서는 `vDSP_dotpr`(Accelerate 프레임워크의 벡터 내적 함수)로 tau별 내적을 구했다. 이중 for-loop로 직접 곱셈-덧셈을 반복하는 대신 Accelerate가 SIMD로 벡터화해서 계산해주기 때문에, tau 후보를 수백~수천 개 훑어도 1프레임(수 ms)이면 끝난다.

### YIN이 일반 자기상관과 다른 점 (4단계)

일반적인 "가장 상관이 높은 tau 찾기" 방식은 배음(harmonics) 때문에 자꾸 원래 주기의 절반이나 2배를 잘못 고르는 **옥타브 오차**가 잦다. YIN(de Cheveigné & Kawahara, 2002)은 이를 줄이기 위해 4단계를 거친다.

1. **차이 함수(difference function) d(tau)**: 상관이 아니라 "차이의 제곱합"을 쓴다. `d(tau) = energy(윈도우) + energy(tau만큼 민 윈도우) - 2×상관(tau)` — 두 파형이 똑같으면 0에 가깝고, 다르면 커진다. (상관이 아니라 차이를 쓰는 이유: 차이는 진폭 크기에 덜 민감해서 더 뚜렷한 골(dip)이 생긴다.)
2. **누적평균정규화(CMNDF)**: `d(tau)`를 "지금까지의 평균 d값"으로 나눠서 정규화한다. 이게 없으면 tau가 작을 때 값이 우연히 작아 보이는 경우가 많아서, 진짜 주기보다 짧은(=더 높은 옥타브의) tau를 잘못 고르기 쉽다.
3. **절대 임계값(absolute threshold)**: CMNDF가 특정 값(threshold, 여기선 0.15) 아래로 처음 떨어지는 지점을 찾고, 거기서 계속 더 내려가는 동안(국소 최소값) 따라간다. "가장 낮은 지점"이 아니라 "처음으로 확실히 낮아지는 지점"을 찾는 게 핵심 — 배음 때문에 더 낮은 골이 다른 tau에 있어도 무시한다.
4. **포물선 보간(parabolic interpolation)**: 위에서 찾은 tau는 정수(샘플 단위)라서 주파수 해상도가 계단식이다. tau 앞뒤 3개 점에 포물선을 맞춰 진짜 최소값의 위치(정수 사이의 실수)를 추정하면 훨씬 정밀한 주파수가 나온다. Phase 1의 ±10 cent 목표는 사실상 이 보간 없이는 달성하기 어렵다.

### 왜 배열(`[PitchCandidate]`)을 반환하나

지금은 후보를 1개(또는 0개, 무음/불확실 시)만 반환하지만, 나중에 pYIN(Probabilistic YIN)으로 확장하면 "여러 후보 tau + 각각의 확률"을 HMM으로 스무딩해서 옥타브 오차를 더 줄인다. 그때 함수 시그니처를 안 바꾸려고 처음부터 배열로 설계했다.

### confidence 값의 의미

`confidence = 1 - CMNDF(tau)`. CMNDF가 0에 가까울수록(골이 깊을수록) "이 tau가 진짜 주기"라는 확신이 크다는 뜻이라, 1에서 빼서 0~1 범위의 신뢰도로 뒤집었다. 나중에 VAD/UI에서 "이 피치 값을 얼마나 믿을지" 판단하는 데 쓸 수 있다.

## 6. VoiceActivityDetector — 에너지 기반 VAD

### 왜 필요한가

YIN은 입력이 순수 잡음이어도 어떻게든 tau를 하나 골라서 "그럴듯한" 주파수를 뱉어낼 수 있다(무음/잡음 구간에서도 CMNDF가 우연히 threshold 아래로 떨어질 수 있음). VAD(Voice Activity Detection)는 "지금 이 프레임에 노래/음성이 실제로 있는가"를 먼저 걸러서, 없으면 YIN 결과 자체를 버리는 역할을 한다. Phase 1 스펙의 "무음/저에너지 구간은 출력하지 않는다" 조건이 이 컴포넌트다.

### 평균 파워(mean square)로 "에너지"를 재는 이유

소리 신호는 양수/음수를 오가는 파형이라 그냥 평균을 내면 서로 상쇄돼서 항상 0에 가깝다. 그래서 각 샘플을 제곱한 뒤 평균을 낸다 — 이게 신호의 "평균 파워"이고, 마이크 입력이 얼마나 큰 소리인지를 부호와 상관없이 나타낸다. 이 값의 제곱근(sqrt)을 취하면 RMS(Root Mean Square)가 되는데, 여기서는 임계값과 크기 비교만 하면 되므로 제곱근 계산은 생략했다 (`meanSquare > threshold` ⟺ `RMS > sqrt(threshold)`이므로 결과는 같다 — 불필요한 연산을 아낀 것).

`vDSP_measqv`가 바로 이 "제곱의 평균"을 한 번의 Accelerate 호출로 계산해주는 함수다.

### 임계값(threshold)은 왜 아직 확정값이 아닌가

지금 넣은 `0.0001`은 시작값일 뿐이다. 실제 마이크 입력의 배경 소음 수준은 기기, 환경(조용한 방 vs 카페), 마이크 게인 설정에 따라 크게 달라지므로, `AudioCapture`를 붙이고 실기기에서 소리를 넣어본 뒤 조정해야 한다 (phase-1-yin-prototype.md의 검증 방법 3번: "잡음이 섞인 환경에서 VAD가 오탐하지 않는지 확인").

## 7. AudioCapture — AVAudioEngine으로 마이크를 붙이기

### AVAudioEngine / AVAudioSession / inputNode

- `AVAudioSession`은 "이 앱이 오디오 하드웨어를 어떤 용도로 쓸지"를 시스템에 알리는 설정 객체다. `.record` 카테고리로 녹음 용도임을 선언하고, `.measurement` 모드를 골랐다 — 이 모드는 시스템이 자동으로 걸어주는 AGC(자동 게인 조절)나 음성 향상 처리를 최소화해서, 원본 파형에 최대한 가까운 신호를 준다. 일반 통화/음악 모드는 사람이 듣기 좋게 신호를 가공하기 때문에 피치 검출에는 오히려 방해가 될 수 있다.
- `AVAudioEngine`은 오디오 입출력 노드들을 연결하는 그래프 엔진이다. `engine.inputNode`가 마이크에 해당하는 노드.
- `installTap(onBus:bufferSize:format:)`: inputNode를 흐르는 오디오를 "엿듣는" 콜백을 건다. 오디오를 사용/변형하지 않고 그냥 관찰만 하는 것이라 "tap(도청)"이라는 이름이 붙었다. 콜백은 정해진 프레임 수(`bufferSize`)만큼 샘플이 모일 때마다 반복 호출된다.

### 버퍼 크기 2048을 고른 이유

버퍼가 클수록 한 번에 더 많은 샘플을 확보해 저음역까지 안정적으로 검출할 수 있지만, 그만큼 "버퍼가 다 찰 때까지" 기다려야 해서 지연이 커진다. 44.1kHz 기준 2048 샘플 = 약 46ms — YINPitchDetector가 80Hz까지 검출하는 데 필요한 tau 탐색 범위(`n/2 >= 551`)를 충분히 만족하면서도, 200ms 지연 목표에 넉넉한 여유(YIN 연산 자체는 1ms 미만)를 남긴다.

### 오디오 스레드와 메인 스레드

`installTap`의 콜백은 UI 스레드가 아니라 **실시간 오디오 스레드**에서 실행된다. 오디오 스레드는 절대 블로킹되면 안 되는데(끊기면 소리가 뚝뚝 끊긴다), SwiftUI의 `@State`는 메인 스레드에서만 안전하게 갱신할 수 있다. 그래서 `computeResult`(VAD→YIN→노트변환, 순수 계산)는 오디오 스레드에서 그대로 실행하되, 결과를 `DispatchQueue.main.async`로 메인 스레드에 넘긴 뒤에야 콜백을 호출하도록 분리했다.

### 이번 단계에서 실제로 연결된 파이프라인

```
마이크 → AVAudioEngine tap(2048샘플)
       → VoiceActivityDetector (무음이면 여기서 버림)
       → YINPitchDetector (기본 주파수 Hz 추정)
       → NoteNameConverter (Hz → 노트명 + cent)
       → 메인 스레드로 전달 → 콘솔 출력 + 화면 표시
```

지금까지 만든 4개 컴포넌트(NoteNameConverter, YINPitchDetector, VoiceActivityDetector, AudioCapture)가 전부 연결되어 Phase 1 완료 조건의 핵심 파이프라인이 동작한다. 다음은 실기기에서 튜너 앱과 비교해 정확도(±10 cent)와 체감 지연(200ms 이내)을 검증하는 단계다.

**Phase 1 실기기 검증 완료(2026-08-15)**: 스피커로 재생한 기준음 대비 ±10 cent 이내 정확도 확인, 저음~고음 글리산도 구간에서도 옥타브 오차 없이 매끄럽게 트래킹됨.

## 8. KeyDetector — 조성 판별 (Krumhansl-Schmuckler 계열)

### 문제: 음 몇 개만 듣고 "이 곡은 무슨 조성인가"를 어떻게 판단하나

사람은 곡을 듣다 보면 자연스럽게 "아, 이건 다장조(C Major)구나" 하고 느끼는데, 이건 어떤 음이 얼마나 "중심적"으로 쓰였는지에 대한 감각이다. 예를 들어 다장조 곡에서는 C(으뜸음)와 G(딸림음)가 자주, 길게 나오고 C#/D#/F#/G#/A# 같은 반음계 밖 음은 거의 안 나온다. 이 패턴을 수치화한 게 **key profile**이다.

### Pitch-class 히스토그램

옥타브는 무시하고(C3든 C5든 그냥 "C") 12개 음이름별로 "이 곡에서 각 음을 총 얼마나 오래 냈는가"를 더한 12칸짜리 막대그래프를 만든다. 이게 이 곡의 "음향적 지문"이다. 여기서 **개수가 아니라 길이로 가중치를 준 이유**는, 스쳐 지나가듯 짧게 낸 경과음(passing tone) 하나가 길게 지속한 진짜 중심음과 똑같은 비중을 가지면 조성 판단이 흔들리기 때문이다(PRD 부록 B에서 명시한 근거).

### Key profile — 경험적으로 정해진 "정답 모양"

Krumhansl & Kessler(1982)가 음악 이론가들에게 "이 조성에서 각 음이 얼마나 안정적으로 들리나요"를 설문해서 12개 숫자로 만든 게 원조다. 여기서는 그 후속 연구인 **Temperley(1999)의 개정판**(실제 바흐 코랄 등 코퍼스 데이터로 재보정, `Kostka-Payne` 프로파일로도 불림)을 썼다 — PRD가 명시적으로 이 버전을 선택했다.

```
장조: [5.0, 2.0, 3.5, 2.0, 4.5, 4.0, 2.0, 4.5, 2.0, 3.5, 1.5, 4.0]
      (도)  (도#) (레) (레#)(미) (파) (파#)(솔) (솔#)(라) (라#)(시)
```
으뜸음(도=5.0)과 딸림음(솔=4.5)이 가장 높고, 반음계 밖 음(레#, 파#, 라#)이 가장 낮다 — 장조 화성에서 실제로 그 음들이 그렇게 쓰이기 때문이다. 단조는 3번째 칸(단3도, "미"에 해당하는 자리)이 장조보다 높게 잡혀 있어서, 장조/단조를 가르는 핵심 단서가 된다.

### 24개 조성 후보와 상관계수(correlation)

C 기준으로 만들어진 이 프로파일을 그대로 D장조에 쓸 순 없으니, 12번 회전시켜서 "각 으뜸음 기준 장조 프로파일" 12개 + "단조 프로파일" 12개, 총 24개 후보를 만든다. 그리고 내가 만든 pitch-class 히스토그램이 이 24개 중 어떤 것과 **모양이 가장 비슷한지**를 피어슨 상관계수(Pearson correlation)로 잰다. 상관계수는 절댓값 크기가 아니라 "패턴의 모양"만 비교하기 때문에(크기 변화·이동에 영향받지 않음), 사람이 크게 부르든 작게 부르든, 길게 부르든 짧게 부르든 상관없이 일관되게 비교할 수 있다. 상관계수가 가장 높은 후보가 정답 조성이다.

### confidence는 왜 "1위 상관계수"가 아니라 "1위-2위 차이"인가

상관계수 자체가 높아도(예: 0.9) 2위 후보도 거의 비슷하게 높으면(0.89) 사실 애매한 상황이다 — 흔한 예로 다장조(C Major)와 그 관계단조인 가단조(A Minor)는 쓰는 음이 완전히 같아서 상관계수가 서로 아주 가깝게 나온다. 그래서 "얼마나 확실한가"는 1위 값 자체보다 **1위와 2위의 격차(margin)**로 판단했다. PRD의 "조성이 모호하면 재녹음을 안내한다" 요구사항을 상위 로직(UI)에서 처리할 때 이 confidence 값을 기준으로 쓰면 된다.

### 왜 여기서 재녹음 안내 로직을 넣지 않았나

`KeyDetector`는 confidence 수치만 계산해서 반환하고, "얼마나 낮으면 재녹음을 안내할지"는 판단하지 않는다. 임계값 정책은 UI/사용자 경험 결정이라 신호처리 로직과 분리해뒀다 — 나중에 실제 데이터로 임계값을 튜닝할 때 이 함수를 건드릴 필요가 없다.

## 9. ChordGenerator — diatonic 3도/5도 화음 생성

### "3도 위"는 반음 개수가 아니라 음계 칸 수

음악에서 "3도"는 반음을 몇 개 세는 게 아니라 **음계 상에서 몇 번째 음인가**를 센다. C장조에서 C의 3도 위는 E(반음 4개 = 장3도)지만, D장조에서 D의 3도 위는 F#(반음 4개 = 역시 장3도, 하지만 흰 건반이 아니라 검은 건반)이다. 그런데 같은 장조라도 시작음에 따라 장3도/단3도가 자동으로 섞인다 — 예를 들어 C장조에서 D 위의 3도는 F(반음 3개 = 단3도)다. `ChordGenerator`가 반음을 직접 세지 않고 **"음계 배열에서 인덱스를 2칸/4칸 이동"** 하는 방식을 쓴 이유가 이것이다 — 이렇게 하면 장3도/단3도를 조성에 맞게 자동으로 올바르게 골라준다("diatonic 화성"의 핵심).

- 3도 위 = 음계 인덱스로 2칸 이동 (예: 인덱스 0인 도 → 인덱스 2인 미)
- 5도 위 = 음계 인덱스로 4칸 이동 (도 → 인덱스 4인 솔)

### MIDI 노트 번호로 계산하는 이유

`KeyDetector`처럼 pitch class(0~11, 옥타브 무관)만으로는 화음을 못 만든다 — "3도 위"가 실제로 몇 Hz인지 알려면 옥타브까지 포함한 절대 음높이(MIDI 노트 번호, 예: C4=60)가 필요하다. `NoteNameConverter`에서 Hz↔MIDI 변환 공식을 재사용 가능한 함수(`exactMIDINote(forFrequency:)`, `frequency(forMIDINote:)`)로 뽑아내서, 여기서 그대로 가져다 쓴다 — 같은 공식(69 + 12·log2(f/440))을 두 파일에 따로 베끼지 않기 위함.

### "항상 멜로디 위로 쌓기" 옥타브 보정

음계 인덱스로 목표 음이름을 찾으면, 그 음이 멜로디와 같은 옥타브 안에서는 멜로디보다 **낮은 자리**에 있을 수도 있다 (예: G4 위의 5도인 D는 같은 옥타브에서 D4=62로 G4=67보다 낮다). "3도 위/5도 위"라는 요구사항상 화음은 항상 멜로디보다 높아야 하므로, 이런 경우 한 옥타브(12 반음)를 더해서 D5(74)로 올린다. 이건 실제 합창/중창에서 위 화음을 붙일 때 자연스러운 보이싱과도 일치한다.

### 온음계에 없는 음(반음계 경과음)은 왜 nil을 반환하나

사용자가 판별된 조성의 온음계 밖의 음(예: C장조에서 C#)을 불렀다면, 그 음 위에 "온음계적으로 올바른" 3도/5도가 정의되지 않는다(반음계 화성은 v1 범위 밖). 억지로 가장 가까운 음계 음으로 스냅하는 대신 nil을 반환해서, 이런 경우를 어떻게 처리할지(무시할지, 반음계 화성으로 확장할지)는 나중에 상위 로직에서 명시적으로 결정하게 열어뒀다.

## 10. MelodySession — 마이크 파이프라인과 KeyDetector/ChordGenerator 연결

### "프레임 단위 결과"를 "조성 판별용 입력"으로 바꾸는 접착제

`KeyDetector`는 "pitch class별로 총 얼마나 오래 냈는가"라는 누적된 통계를 원하는데, `AudioCapture`는 ~46ms짜리 프레임 하나하나에 대해 콜백을 부른다. `MelodySession`은 이 둘 사이를 잇는다 — 매 프레임이 들어올 때마다 "이 프레임 길이(frameDuration)만큼 이 pitch class에 더한다"를 반복해서, 자연스럽게 "길이 가중치가 반영된 pitch-class 히스토그램"을 쌓는다. 온셋/오프셋(음이 언제 시작하고 끝나는지)을 따로 검출하지 않고도, 프레임 단위 누적만으로 근사가 되는 셈이다 — 정교하지는 않지만 프로토타입 단계에서는 충분하다.

### 왜 클래스(참조 타입)로 만들었나

`KeyDetector`, `ChordGenerator`와 달리 `MelodySession`은 `enum`이 아니라 `final class`다. 이 컴포넌트는 "지금까지 부른 멜로디"라는 **상태**를 세션 내내 유지해야 하기 때문이다(사용자가 "다시 시작"을 누르기 전까지 계속 쌓임). `AudioCapture`와 같은 이유로 순수 함수가 아니라 상태를 가진 I/O 인접 컴포넌트로 분류했다 — 다만 실제 "판단"(조성이 뭔지, 화음이 뭔지)은 여전히 `KeyDetector`/`ChordGenerator`라는 순수 함수에 그대로 위임하고, 이 클래스는 상태 누적과 그 상태를 순수 함수 입력 형태로 변환하는 역할만 한다.

### 무음 프레임(nil)을 무시하는 이유

VAD가 걸러낸 무음 프레임까지 pitch class 0(C)처럼 취급해서 누적하면 조성 판별이 완전히 틀어진다. `record(_:)`가 `nil`을 받으면 아무 것도 하지 않고 조용히 넘어가도록 만들어서, 이 문제를 원천 차단했다.

### 화면에 보이는 값의 의미

- **조성**: 지금까지 부른 멜로디 전체의 누적 통계 기준 — 노래를 더 부를수록 계속 갱신되고, 보통 더 안정적으로 수렴한다.
- **화음 제안**: 그 조성을 기준으로 "마지막으로 부른 한 음" 위에 3도/5도를 쌓은 것 — 매 프레임 바뀔 수 있다(멜로디가 계속 움직이므로).

## 11. TonePlayer — 화음 목표음 재생 (Phase 3 착수)

### 왜 필요한가

`ChordGenerator`가 "E4, G4"라는 화음을 제안해도, 그게 실제로 맞는 제안인지 텍스트만 봐서는 알기 어렵다. 가장 직접적인 검증 방법은 **그 소리를 실제로 들어보는 것**이다. `TonePlayer`는 지정한 주파수의 순수 사인파(배음이 없는 가장 단순한 파형)를 계속 재생해서, 방금 부른 멜로디와 제안된 화음이 실제로 귀에 어울리는지 바로 확인할 수 있게 한다. Phase 3의 "목표음 재생" 요구사항의 첫걸음이자, 나중에 "이 목표음을 따라 불러보세요" 훈련의 기준음으로도 그대로 재사용된다.

### AVAudioSourceNode — 코드로 직접 소리를 "생성"하기

지금까지 오디오는 항상 마이크에서 "들어오는" 쪽만 다뤘다(`AVAudioEngine.inputNode`). `TonePlayer`는 반대로 오디오를 "만들어서 내보내는" 쪽이다. `AVAudioSourceNode`는 오디오 엔진이 매 프레임마다 스피커로 내보낼 샘플이 필요할 때 호출하는 콜백을 등록하는 노드다 — 이 콜백 안에서 사인 함수 값을 계산해 버퍼를 채워 넣으면, 그게 그대로 소리가 되어 나간다.

```swift
sample = sin(phase) * amplitude
phase += 2π × frequency / sampleRate   // 매 샘플마다 위상을 이만큼 전진시킨다
```
`phase`(위상)가 한 바퀴(2π) 도는 데 걸리는 샘플 수가 정확히 `sampleRate / frequency`가 되도록 맞춘 것 — 이게 바로 "주파수"의 정의(초당 반복 횟수)를 코드로 옮긴 것이다.

### 그래프를 한 번만 만드는 이유 — 소리가 겹쳐 쌓이는 버그

처음 구현에서는 재생 버튼을 누를 때마다 새 `AVAudioSourceNode`를 만들어 엔진에 붙였는데, 이러면 이전에 붙였던 노드가 엔진 그래프에서 제거되지 않은 채 남아있어서 **재생을 반복할수록 오래된 톤들이 겹쳐서 계속 들리는** 문제가 생긴다. 그래서 노드 연결(그래프 구성)은 최초 1번만 하고, 이후 재생/정지는 `engine.start()`/`engine.pause()`로 오디오 엔진 자체를 멈췄다 재개하는 방식으로 바꿨다 — 그래프는 그대로 두고 "흐르게 할지 말지"만 켜고 끄는 것.

### `.playAndRecord`로 카테고리를 바꾼 이유와 트레이드오프

지금까지는 `.record`(녹음 전용) 카테고리를 썼는데, 이제 마이크로 듣는 동시에 스피커로 소리를 내야 하므로 `.playAndRecord`로 바꿨다. 문제는 **스피커로 나간 소리가 다시 마이크로 들어가 섞일 수 있다**는 점이다(음향학적 피드백/에코) — 통화 앱들은 이걸 막으려고 AEC(음향 반향 제거) 처리를 쓰는데, 우리는 `.measurement` 모드를 쓰는 한 그런 처리가 최소화되어 있어서 이 문제에 더 취약하다. 재생 볼륨을 낮게 잡아서 완화하는 방법도 있지만, 실기기에서 테스트해보니 너무 안 들려서(0.15 -> 0.6) 오히려 키웠다 — 근본적으로는 이어폰/헤드폰 사용을 권장하거나, "듣기"와 "부르기"를 완전히 분리된 단계로 나누는 UX가 더 안전하다. Phase 3 UI를 다듬을 때 다시 고려할 지점.

### 화음의 음을 하나씩 순서대로 들려주는 이유

처음엔 3도 음 하나만 계속 재생했는데, "화음이 맞는지 확인"하려면 3도와 5도를 각각 따로 들어봐야 판단하기 쉽다(두 음을 동시에 섞어 재생하면 초보자 귀에는 구분이 잘 안 된다). 그래서 `ContentView.playHarmonyNotesInSequence()`가 화음 배열을 한 음씩(0.8초씩) 순환 재생하도록 바꿨다. 이 루프는 매 바퀴마다 `melodySession.suggestedHarmony`를 다시 읽기 때문에, 재생 중에 계속 노래를 이어 부르면 다음 바퀴부터 최신 화음을 자동으로 반영한다 — 즉 "지금까지 부른 멜로디에 실시간으로 맞는 화음"을 계속 따라간다. (파일로 녹음된 멜로디를 입력하는 기능은 아직 없다 — 지금은 마이크 실시간 입력만 지원하고, 파일 입력은 PRD에서 Could-have로 남겨둔 v2 스코프다.)

### 재생 루프와 프레임 콜백이 동시에 주파수를 건드리면 안 되는 이유

전에는 마이크 콜백 안에서 "재생 중이면 최신 3도로 주파수를 갱신"하는 코드가 있었는데, 이제 재생 루프(`playHarmonyNotesInSequence`)가 자기 페이스(0.8초마다)로 주파수를 갱신하는 역할을 전담하므로 이 코드를 지웠다. 두 곳에서 동시에 `tonePlayer.setFrequency()`를 부르면 어느 쪽이 마지막에 이겼는지에 따라 음이 매 프레임(46ms)마다 널뛰듯 바뀌어서 화음처럼 안 들리고 지저분하게 흔들리는 소리가 났을 것이다.

### 스피커 소리가 마이크로 되먹임되는 피드백 루프 — 실제로 터진 버그

`.playAndRecord` 카테고리로 바꾸면서 우려했던 문제(위 항목)가 실제로 발생했다: 화음을 재생하면 그 소리가 마이크로 다시 들어가서 `YINPitchDetector`가 "새로 부른 음"으로 감지하고, `MelodySession`이 그걸 `lastNote`로 기록한 뒤, 그 음 위에 또 새 화음을 제안하고, `TonePlayer`가 그 새 화음을 재생하고... 이런 식으로 **재생 → 재인식 → 새 제안 → 재생**이 꼬리를 물고 이어지는 피드백 루프가 생겼다. 사용자 입장에서는 버튼 한 번 눌렀는데 화음이 계속 다른 음으로 바뀌는 것처럼 보였다.

해결: 재생 중(`isPlayingTone == true`)에는 마이크 콜백 맨 앞에서 즉시 `return`해서 `MelodySession.record()` 자체를 호출하지 않는다 — 재생 중엔 마이크 입력을 통째로 무시하는 것. 그리고 재생할 화음은 버튼을 누른 시점에 `melodySession.suggestedHarmony`를 한 번만 읽어서 지역 변수(`lockedHarmony`)로 고정한 뒤, 재생 루프는 그 고정된 배열만 반복 재생한다 — 매 바퀴 다시 읽지 않는다. 이렇게 하면 "다시 시작을 누르기 전까지는 이 음에 대한 화음만 듣는다"는 사용자 기대와 정확히 일치하고, 재생 중 들어온(사실은 스피커에서 나간) 소리가 `MelodySession`의 누적 통계를 오염시키는 것도 막는다.

## 12. PitchScorer + 콜앤리스폰스 채점 — Phase 3 실시간 채점

### 3도/5도를 각각 채점하기

처음엔 "채점 시작" 버튼 하나가 항상 3도만 목표로 삼았는데, 화음은 3도와 5도 두 음으로 이뤄지니 둘 다 연습할 수 있어야 한다. 그래서 버튼을 "3도 채점" / "5도 채점" 두 개로 나누고, `toggleScoring(interval:)`이 `ChordGenerator.HarmonyNote` 배열에서 해당 interval을 찾아 목표로 고정하도록 바꿨다. 채점 중에 반대쪽 버튼을 누르면 멈췄다 다시 시작하는 게 아니라 **바로 목표를 전환**한다 — 3도/5도를 번갈아 연습할 때 매번 중지 버튼을 따로 누르는 불편을 없애기 위함. 목표가 바뀔 때마다 `pitchSmoother.reset()`도 같이 호출해서, 이전 목표음 근처에서 쌓인 스무딩 값이 새 목표 채점에 섞여 들어가지 않게 한다.

### 왜 "재생하면서 동시에 채점"하지 않았나

PRD가 그리는 이상적인 그림은 "목표 화음이 계속 울리는 동안 그걸 들으며 따라 부르고, 편차가 실시간으로 표시되는" 것이다. 하지만 지금 구조(스피커+마이크를 동시에 쓰고 AEC 없는 `.measurement` 모드)에서는 목표음을 재생하면서 동시에 마이크로 사용자 목소리만 깨끗이 구분해 듣는 게 사실상 불가능하다 — 방금 11절에서 겪은 피드백 루프가 바로 그 증거다. 그래서 이번 프로토타입은 **콜앤리스폰스(call-and-response)** 방식으로 스코프를 좁혔다: (1) 목표음을 듣는다 → (2) 재생이 멈추면 마이크가 다시 켜진다 → (3) 그 목표음을 기억하며 따라 부르면 실시간으로 채점된다. 동시 재생+채점은 나중에 이어폰 전제, 또는 AEC가 있는 다른 오디오 세션 모드를 조사한 뒤 다시 시도해볼 만한 확장 지점으로 남겨둔다.

### PitchScorer가 NoteNameConverter와 다른 점

`NoteNameConverter.centsOffset`은 "가장 가까운 평균율 음(12개 중 하나)"과의 차이를 잰다. 반면 `PitchScorer`는 그 12개 중 하나가 아니라 **임의의 목표 주파수 하나**(예: 화음의 3도 음, 정확히는 391.995...Hz 같은 값)와의 차이를 잰다. 계산식은 똑같이 `1200 × log2(비율)`(cent는 정의상 반음의 1/100이고, 반음 하나는 주파수비 2^(1/12)이므로, 두 주파수의 비율에 로그를 취해 반음 단위로 환산한 뒤 100을 곱한 것)이지만, 비교 대상이 "고정된 평균율 격자"냐 "임의의 목표음 하나"냐가 다르다.

### 허용 오차(±35 cent)는 왜 그 값인가

100 cent가 반음 하나이므로, 35 cent는 반음의 1/3 조금 넘는 정도다. 이 값은 엄밀한 근거보다는 "너무 빡빡하면 초보자는 다 틀렸다고 나오고, 너무 널널하면 반음 옆 음도 맞았다고 나오는" 균형점을 잡은 시작값이다 — 실제 사용자 테스트를 거쳐 조정이 필요한 값이라는 걸 코드 주석에도 남겨뒀다.

### UI를 "번호가 붙은 단계"로 재구성한 이유

지금까지는 상태 텍스트와 버튼들이 그냥 세로로 나열돼 있어서, 화면만 보고는 "이게 지금 파이프라인의 어느 단계인지" 알기 어려웠다. `ContentView`를 1.실시간 피치 → 2.조성 판별 → 3.화음 제안 → 4.따라 부르기 채점, 이렇게 번호 붙은 섹션(`flowSection`)으로 나눠서, 화면 구조 자체가 `AudioCapture → KeyDetector → ChordGenerator/TonePlayer → PitchScorer`로 이어지는 실제 데이터 흐름과 그대로 대응되게 했다. 디자인을 다듬은 건 아니고, "지금 무슨 일이 일어나고 있는지"를 한눈에 보이게 하는 최소한의 정리다.

### PitchMeterView — 숫자 대신 바늘로 보여주기

`%+.0f cent`처럼 텍스트로 숫자를 보여주면, "지금 내가 높게 부르고 있는지 낮게 부르고 있는지"를 머릿속으로 다시 해석해야 한다. 기타 튜너 앱들이 전부 바늘/막대 형태의 시각적 미터를 쓰는 이유가 이거다 — 왼쪽/오른쪽이라는 공간적 위치가 "낮음/높음"이라는 의미와 자연스럽게 대응돼서 해석 과정이 필요 없다.

- **가로 위치 매핑**: `cents / displayRangeCents`(±50cent를 화면 폭 전체로 잡음) 비율을 계산해서 중앙(0cent)을 기준으로 좌우로 이동시킨다. ±35cent보다 넓은 ±50cent를 표시 범위로 잡은 이유는, 허용오차 범위(±35)만 딱 맞춰 잡으면 조금만 벗어나도 바늘이 화면 끝까지 튀어서 "얼마나" 벗어났는지 구분이 안 되기 때문이다.
- **허용오차 구간 음영**: `PitchScorer.onPitchToleranceCents`(±35cent)에 해당하는 폭만큼 중앙에 초록색 음영을 깔아서, 바늘이 그 구간 안에 들어오면 "정확" 판정이라는 걸 굳이 텍스트를 안 봐도 알 수 있게 했다.
- **clamp 처리**: 표시 범위(±50cent)를 벗어나는 극단적인 편차는 막대 끝에 붙여서(clamp) 보여준다 — 튜너 앱들도 대부분 이렇게 하는데, 안 그러면 옥타브 단위로 완전히 다른 음을 불렀을 때 바늘이 미터 밖으로 나가버려서 UI가 깨진 것처럼 보인다.

## 13. PitchSmoother — 비브라토로 튀는 값을 눌러주기

### 왜 필요했나

바늘 미터를 실기기에서 써보니 "음이 샵도 되고 플랫도 나고 막 흔들린다"는 문제가 있었다. 이건 버그가 아니라 **사람 목소리의 본질적인 특성**이다 — 아무리 안정적으로 부르려 해도 성대는 초당 몇 번씩 미세하게 떨리고(비브라토), 음을 처음 낼 때는 정확한 피치에 안착하기까지 약간의 시간이 걸린다(온셋 불안정). YIN은 이걸 있는 그대로, 프레임(약 46ms)마다 정직하게 측정해서 보여주기 때문에 원본 값 그대로는 미터가 지저분하게 떨린다. PRD 부록 B에도 "비브라토는 프레임 단위 편차의 이동평균으로 스무딩" 이라고 이미 이 보완책이 예정되어 있었다.

### 왜 Hz가 아니라 MIDI 노트(로그 스케일)에서 평균을 내나

`NoteNameConverter`에서 다뤘듯 피치는 로그적으로 지각된다. 만약 411Hz와 466Hz(반음 차이가 다른 두 저음역 예시)를 그냥 Hz 단위로 평균 내면, 저음역과 고음역에서 "같은 반음 차이"가 평균 계산에 서로 다른 영향을 준다. MIDI 노트 번호로 변환한 뒤 평균을 내면(그리고 다시 Hz로 변환하면), 음역대에 상관없이 일관된 스무딩이 된다.

### 지수이동평균(EMA)이 하는 일

```
새 평균값 = 이전 평균값 + factor × (이번 측정값 - 이전 평균값)
```
`factor`(0.3)가 클수록 최신 값에 더 민감하게 반응하고(반응은 빠르지만 덜 부드러움), 작을수록 여러 프레임에 걸쳐 더 부드럽게 움직인다(부드럽지만 반응이 느려짐). 매 프레임 전체 이력을 저장하지 않고 "이전 평균값 하나"만 기억하면 되기 때문에, 이동평균(moving average)보다 구현이 간단하고 메모리도 적게 쓴다 — 그래서 실시간 오디오 처리에서 자주 쓰인다.

### 어디에 적용했고, 어디엔 안 했나

1단계(실시간 피치) 표시는 원본 값을 그대로 보여준다 — Phase 1의 "검출된 주파수를 있는 그대로 보여준다"는 요구사항, 그리고 디버깅 시 원본 신호를 확인할 수 있어야 한다는 이유 때문이다. 반면 4단계(채점)에서 `PitchScorer`에 넘기는 값은 스무딩을 거친다 — 채점의 목적은 "지금 대충 맞는 음을 내고 있는지"를 판단하는 것이라, 순간적인 흔들림보다 안정된 경향이 더 중요하기 때문이다.

## 14. 단음 캡처 모드 — "일단 한 음만" 고정하기

### 왜 필요했나

`MelodySession`은 원래 "계속 부르는 멜로디 전체"를 누적하도록 설계했는데, 지금 단계에서 실제로 마이크에 들어오는 건 숨소리, 다음 음절, 주변 잡음 등 온갖 소리가 섞여 있다. 매 프레임 `lastNote`가 갱신되니, 사용자가 의도한 것과 무관하게 조성·화음이 계속 바뀌었다 — "지금은 단음으로만, 음 하나가 들어가면 그 음에 맞는 화음이 고정돼야 한다"는 사용자 피드백대로, 나중에 곡 전체를 듣고 여러 화음을 뽑아내는 기능(진짜 `MelodySession`의 원래 목적)과는 별개로, 지금은 "한 음만 잡아서 고정"하는 게 필요했다.

### 스트릭(streak) 확정 — 잡음 한 프레임에 안 속기

VAD를 통과했다고 다 "진짜 노래하는 음"은 아니다 — "음"이나 "스" 같은 자음의 순간적 파열음도 짧게는 YIN에 걸릴 수 있다. 그래서 pitch class(옥타브 무관 음이름)가 **연속으로 3프레임(약 140ms) 같은 값**을 유지해야만 그 음으로 확정한다. 1프레임(46ms)이면 순간적인 잡음일 수도 있지만, 140ms 동안 같은 음이 유지된다는 건 실제로 그 음을 내고 있다는 뜻에 가깝다.

### 화면 갱신을 "표시"와 "판단"으로 분리

1단계(실시간 피치) 텍스트는 음을 확정한 뒤에도 계속 갱신된다 — 지금 마이크가 뭘 듣고 있는지 보여주는 순수 정보 표시라서 막을 이유가 없다. 반면 `MelodySession`에 기록하는 것(조성/화음이 바뀌는 원인)은 `hasCapturedNote`가 `true`가 되는 순간 멈춘다. 그리고 4단계 채점(`PitchScorer`)은 이 둘과 별개로 계속 돌아간다 — 채점은 "이미 고정된 목표음을 얼마나 잘 따라 부르는지"를 보는 것이라, 오히려 확정 이후에도 계속 마이크를 들어야 하기 때문이다. 이렇게 "언제 멈추고 언제 계속 돌아야 하는지"가 컴포넌트마다 다르다는 걸 하나의 콜백 안에서 조건문으로 구분해서 처리했다.
