# 학습 노트 — 기술 & 개념 정리

이 문서는 하모니업(Harmony Up)을 만들면서 사용한 기술과 개념을, 나중에 다시 봐도 이해할 수 있게 풀어서 정리한 것이다. 단계가 끝날 때마다 이어서 추가한다. iOS 개발 경험은 있지만 DSP(디지털 신호 처리)는 이번에 처음 배운다는 전제로 쓴다.

## 1. 프로젝트 구성 — XcodeGen

**뭘 썼나**: `project.yml`이라는 텍스트 파일 하나로 `.xcodeproj`(Xcode 프로젝트 파일)를 자동 생성하는 도구.

**왜 쓰나**: `.xcodeproj`는 내부적으로 XML 비슷한 구조인데, 여러 사람이 동시에 파일을 추가/삭제하면 git 충돌이 잘 난다. `project.yml`은 사람이 읽기 쉬운 YAML이라 충돌이 거의 안 나고, "타깃에 어떤 소스 폴더가 들어가는지"가 한눈에 보인다. 새 `.swift` 파일을 추가해도 Xcode에서 일일이 타깃 멤버십을 체크할 필요 없이, 폴더에 파일만 넣고 `xcodegen generate`만 다시 돌리면 된다.

**우리 프로젝트 구조**:
```
HarmonyUp/
  project.yml              # 타깃 정의(HarmonyUp 앱, HarmonyUpTests)
  HarmonyUp/Sources/        # 앱 타깃 소스
    PitchEngine/            # 신호처리 순수 로직 (UI와 분리)
  HarmonyUp/Tests/           # 유닛 테스트
```

## 2. SwiftUI 앱 기본 구조

- `@main struct HarmonyUpApp: App`: 앱의 진입점. `App` 프로토콜을 채택한 타입에 `@main`을 붙이면 이게 실행 시작점이 된다 (예전 `AppDelegate`의 `UIApplicationMain` 역할을 대체).

## 3. NoteNameConverter — Hz를 음이름으로

### MIDI 노트 번호와 로그 스케일

사람이 듣는 음높이는 주파수(Hz)에 대해 **선형이 아니라 로그(log) 관계**다. 예를 들어 A4(440Hz)에서 한 옥타브 위인 A5는 880Hz — 즉 옥타브가 하나 올라갈 때마다 주파수는 정확히 2배가 된다. 이런 특성 때문에 음악에서는 주파수 대신 "MIDI 노트 번호"라는 로그 스케일 번호를 쓴다.

공식:
```
MIDI 노트 번호 = 69 + 12 × log2(주파수 / 440)
```
- `69`는 A4의 MIDI 번호로 정해진 기준값.
- `12`를 곱하는 이유: 한 옥타브(주파수 2배) 안에 반음(semitone)이 12개 있기 때문. `log2(2) = 1`이므로 옥타브가 하나 올라가면 이 공식은 정확히 `12`만큼 증가한다.
- 결과값을 반올림하면 가장 가까운 반음(= 노트)을 찾을 수 있고, `번호 % 12`로 음이름(C, C#, D…)을, `번호 / 12 - 1`로 옥타브를 구한다.

이건 **평균율(equal temperament)** 튜닝 체계를 전제로 한다 — 한 옥타브를 12개의 반음으로 "똑같은 비율"로 나눈 현대 서양음악 표준 조율법. (참고로 국악 등 다른 음악 체계는 이 전제가 안 맞을 수 있지만, v1 스코프 밖.)

### Cent — 음정 오차의 단위

반음 하나를 다시 100등분한 단위가 **cent**다. "±10 cent 이내 정확도"라는 Phase 1 완료 조건은 반음의 1/10 이내 오차를 뜻한다. 위 공식에서 반올림 전 소수값과 반올림 후 정수값의 차이에 100을 곱하면 cent 단위 편차가 나온다 — 나중에 튜너 앱과 비교 검증할 때 이 값을 쓴다.

### 왜 nil을 반환하게 했나

주파수가 0 이하인 경우(무음/무효 입력)를 호출하는 쪽에서 억지로 필터링하게 만들지 않고, 함수 스스로 "이 입력엔 답이 없다"를 표현하도록 Optional을 리턴 타입으로 썼다. Swift에서 실패 가능한 순수 함수를 표현하는 표준적인 방법.

## 4. 코딩 컨벤션 관련 — 왜 순수 함수로 분리하나

`PitchEngine` 폴더 아래 로직들은 전부 "입력을 받아 출력을 반환"하고, 마이크나 UI 상태 같은 외부 상태를 건드리지 않는 순수 함수/타입으로 설계한다. 이렇게 하면:
- 실제 마이크 없이도 사인파 같은 가짜 입력으로 유닛 테스트가 가능하다 (XCTest).
- 나중에 pYIN으로 알고리즘을 바꾸거나 튜닝값을 조정할 때, UI나 오디오 캡처 코드를 안 건드리고 이 폴더만 수정하면 된다.

## 5. YINPitchDetector — YIN 알고리즘

### 문제: 컴퓨터는 왜 "음높이"를 바로 못 읽나

마이크로 들어온 소리는 시간에 따른 진폭 값의 배열(파형)일 뿐이다. 이 파형이 "1초에 몇 번 반복되는가(주기, period)"를 알아내면 그 역수가 기본 주파수(F0)다. YIN은 이 반복 주기를 찾는 알고리즘이다.

### 자기상관(Autocorrelation)이 하는 일

파형을 자기 자신과 비교하되, 한쪽을 tau(샘플 개수)만큼 밀어서 겹쳐본다. 밀린 정도가 실제 주기와 일치하면 두 파형이 거의 똑같아 보이고, 아니면 안 맞아떨어진다. "두 벡터가 얼마나 비슷한가"는 벡터 내적(dot product)으로 잴 수 있다 — 내적이 크면 비슷한 방향(비슷한 파형), 작으면 다른 방향. 이 프로젝트에서는 `vDSP_dotpr`(Accelerate 프레임워크의 벡터 내적 함수)로 tau별 내적을 구했다. 이중 for-loop로 직접 곱셈-덧셈을 반복하는 대신 Accelerate가 SIMD로 벡터화해서 계산해주기 때문에, tau 후보를 수백~수천 개 훑어도 1프레임(수 ms)이면 끝난다.

### YIN이 일반 자기상관과 다른 점 (4단계)

일반적인 "가장 상관이 높은 tau 찾기" 방식은 배음(harmonics) 때문에 자꾸 원래 주기의 절반이나 2배를 잘못 고르는 **옥타브 오차**가 잦다. YIN(de Cheveigné & Kawahara, 2002)은 이를 줄이기 위해 4단계를 거친다.

1. **차이 함수(difference function) d(tau)**: 상관이 아니라 "차이의 제곱합"을 쓴다. `d(tau) = energy(윈도우) + energy(tau만큼 민 윈도우) - 2×상관(tau)` — 두 파형이 똑같으면 0에 가깝고, 다르면 커진다. (상관이 아니라 차이를 쓰는 이유: 차이는 진폭 크기에 덜 민감해서 더 뚜렷한 골(dip)이 생긴다.)
2. **누적평균정규화(CMNDF)**: `d(tau)`를 "지금까지의 평균 d값"으로 나눠서 정규화한다. 이게 없으면 tau가 작을 때 값이 우연히 작아 보이는 경우가 많아서, 진짜 주기보다 짧은(=더 높은 옥타브의) tau를 잘못 고르기 쉽다.
3. **절대 임계값(absolute threshold)**: CMNDF가 특정 값(threshold, 여기선 0.15) 아래로 처음 떨어지는 지점을 찾고, 거기서 계속 더 내려가는 동안(국소 최소값) 따라간다. "가장 낮은 지점"이 아니라 "처음으로 확실히 낮아지는 지점"을 찾는 게 핵심 — 배음 때문에 더 낮은 골이 다른 tau에 있어도 무시한다.
4. **포물선 보간(parabolic interpolation)**: 위에서 찾은 tau는 정수(샘플 단위)라서 주파수 해상도가 계단식이다. tau 앞뒤 3개 점에 포물선을 맞춰 진짜 최소값의 위치(정수 사이의 실수)를 추정하면 훨씬 정밀한 주파수가 나온다. Phase 1의 ±10 cent 목표는 사실상 이 보간 없이는 달성하기 어렵다.

### 왜 배열(`[PitchCandidate]`)을 반환하나

지금은 후보를 1개(또는 0개, 무음/불확실 시)만 반환하지만, 나중에 pYIN(Probabilistic YIN)으로 확장하면 "여러 후보 tau + 각각의 확률"을 HMM으로 스무딩해서 옥타브 오차를 더 줄인다. 그때 함수 시그니처를 안 바꾸려고 처음부터 배열로 설계했다.

### confidence 값의 의미

`confidence = 1 - CMNDF(tau)`. CMNDF가 0에 가까울수록(골이 깊을수록) "이 tau가 진짜 주기"라는 확신이 크다는 뜻이라, 1에서 빼서 0~1 범위의 신뢰도로 뒤집었다. 나중에 VAD/UI에서 "이 피치 값을 얼마나 믿을지" 판단하는 데 쓸 수 있다.

## 6. VoiceActivityDetector — 에너지 기반 VAD

### 왜 필요한가

YIN은 입력이 순수 잡음이어도 어떻게든 tau를 하나 골라서 "그럴듯한" 주파수를 뱉어낼 수 있다(무음/잡음 구간에서도 CMNDF가 우연히 threshold 아래로 떨어질 수 있음). VAD(Voice Activity Detection)는 "지금 이 프레임에 노래/음성이 실제로 있는가"를 먼저 걸러서, 없으면 YIN 결과 자체를 버리는 역할을 한다. Phase 1 스펙의 "무음/저에너지 구간은 출력하지 않는다" 조건이 이 컴포넌트다.

### 평균 파워(mean square)로 "에너지"를 재는 이유

소리 신호는 양수/음수를 오가는 파형이라 그냥 평균을 내면 서로 상쇄돼서 항상 0에 가깝다. 그래서 각 샘플을 제곱한 뒤 평균을 낸다 — 이게 신호의 "평균 파워"이고, 마이크 입력이 얼마나 큰 소리인지를 부호와 상관없이 나타낸다. 이 값의 제곱근(sqrt)을 취하면 RMS(Root Mean Square)가 되는데, 여기서는 임계값과 크기 비교만 하면 되므로 제곱근 계산은 생략했다 (`meanSquare > threshold` ⟺ `RMS > sqrt(threshold)`이므로 결과는 같다 — 불필요한 연산을 아낀 것).

`vDSP_measqv`가 바로 이 "제곱의 평균"을 한 번의 Accelerate 호출로 계산해주는 함수다.

### 임계값(threshold)은 왜 아직 확정값이 아닌가

지금 넣은 `0.0001`은 시작값일 뿐이다. 실제 마이크 입력의 배경 소음 수준은 기기, 환경(조용한 방 vs 카페), 마이크 게인 설정에 따라 크게 달라지므로, `AudioCapture`를 붙이고 실기기에서 소리를 넣어본 뒤 조정해야 한다 (phase-1-yin-prototype.md의 검증 방법 3번: "잡음이 섞인 환경에서 VAD가 오탐하지 않는지 확인").

## 7. AudioCapture — AVAudioEngine으로 마이크를 붙이기

### AVAudioEngine / AVAudioSession / inputNode

- `AVAudioSession`은 "이 앱이 오디오 하드웨어를 어떤 용도로 쓸지"를 시스템에 알리는 설정 객체다. `.record` 카테고리로 녹음 용도임을 선언하고, `.measurement` 모드를 골랐다 — 이 모드는 시스템이 자동으로 걸어주는 AGC(자동 게인 조절)나 음성 향상 처리를 최소화해서, 원본 파형에 최대한 가까운 신호를 준다. 일반 통화/음악 모드는 사람이 듣기 좋게 신호를 가공하기 때문에 피치 검출에는 오히려 방해가 될 수 있다.
- `AVAudioEngine`은 오디오 입출력 노드들을 연결하는 그래프 엔진이다. `engine.inputNode`가 마이크에 해당하는 노드.
- `installTap(onBus:bufferSize:format:)`: inputNode를 흐르는 오디오를 "엿듣는" 콜백을 건다. 오디오를 사용/변형하지 않고 그냥 관찰만 하는 것이라 "tap(도청)"이라는 이름이 붙었다. 콜백은 정해진 프레임 수(`bufferSize`)만큼 샘플이 모일 때마다 반복 호출된다.

### 버퍼 크기 2048을 고른 이유

버퍼가 클수록 한 번에 더 많은 샘플을 확보해 저음역까지 안정적으로 검출할 수 있지만, 그만큼 "버퍼가 다 찰 때까지" 기다려야 해서 지연이 커진다. 44.1kHz 기준 2048 샘플 = 약 46ms — YINPitchDetector가 80Hz까지 검출하는 데 필요한 tau 탐색 범위(`n/2 >= 551`)를 충분히 만족하면서도, 200ms 지연 목표에 넉넉한 여유(YIN 연산 자체는 1ms 미만)를 남긴다.

### 오디오 스레드와 메인 스레드

`installTap`의 콜백은 UI 스레드가 아니라 **실시간 오디오 스레드**에서 실행된다. 오디오 스레드는 절대 블로킹되면 안 되는데(끊기면 소리가 뚝뚝 끊긴다), SwiftUI의 `@State`는 메인 스레드에서만 안전하게 갱신할 수 있다. 그래서 `computeResult`(VAD→YIN→노트변환, 순수 계산)는 오디오 스레드에서 그대로 실행하되, 결과를 `DispatchQueue.main.async`로 메인 스레드에 넘긴 뒤에야 콜백을 호출하도록 분리했다.

### 이번 단계에서 실제로 연결된 파이프라인

```
마이크 → AVAudioEngine tap(2048샘플)
       → VoiceActivityDetector (무음이면 여기서 버림)
       → YINPitchDetector (기본 주파수 Hz 추정)
       → NoteNameConverter (Hz → 노트명 + cent)
       → 메인 스레드로 전달 → 콘솔 출력 + 화면 표시
```

지금까지 만든 4개 컴포넌트(NoteNameConverter, YINPitchDetector, VoiceActivityDetector, AudioCapture)가 전부 연결되어 Phase 1 완료 조건의 핵심 파이프라인이 동작한다. 다음은 실기기에서 튜너 앱과 비교해 정확도(±10 cent)와 체감 지연(200ms 이내)을 검증하는 단계다.

**Phase 1 실기기 검증 완료(2026-08-15)**: 스피커로 재생한 기준음 대비 ±10 cent 이내 정확도 확인, 저음~고음 글리산도 구간에서도 옥타브 오차 없이 매끄럽게 트래킹됨.

## 8. KeyDetector — 조성 판별 (Krumhansl-Schmuckler 계열)

### 문제: 음 몇 개만 듣고 "이 곡은 무슨 조성인가"를 어떻게 판단하나

사람은 곡을 듣다 보면 자연스럽게 "아, 이건 다장조(C Major)구나" 하고 느끼는데, 이건 어떤 음이 얼마나 "중심적"으로 쓰였는지에 대한 감각이다. 예를 들어 다장조 곡에서는 C(으뜸음)와 G(딸림음)가 자주, 길게 나오고 C#/D#/F#/G#/A# 같은 반음계 밖 음은 거의 안 나온다. 이 패턴을 수치화한 게 **key profile**이다.

### Pitch-class 히스토그램

옥타브는 무시하고(C3든 C5든 그냥 "C") 12개 음이름별로 "이 곡에서 각 음을 총 얼마나 오래 냈는가"를 더한 12칸짜리 막대그래프를 만든다. 이게 이 곡의 "음향적 지문"이다. 여기서 **개수가 아니라 길이로 가중치를 준 이유**는, 스쳐 지나가듯 짧게 낸 경과음(passing tone) 하나가 길게 지속한 진짜 중심음과 똑같은 비중을 가지면 조성 판단이 흔들리기 때문이다(PRD 부록 B에서 명시한 근거).

### Key profile — 경험적으로 정해진 "정답 모양"

Krumhansl & Kessler(1982)가 음악 이론가들에게 "이 조성에서 각 음이 얼마나 안정적으로 들리나요"를 설문해서 12개 숫자로 만든 게 원조다. 여기서는 그 후속 연구인 **Temperley(1999)의 개정판**(실제 바흐 코랄 등 코퍼스 데이터로 재보정, `Kostka-Payne` 프로파일로도 불림)을 썼다 — PRD가 명시적으로 이 버전을 선택했다.

```
장조: [5.0, 2.0, 3.5, 2.0, 4.5, 4.0, 2.0, 4.5, 2.0, 3.5, 1.5, 4.0]
      (도)  (도#) (레) (레#)(미) (파) (파#)(솔) (솔#)(라) (라#)(시)
```
으뜸음(도=5.0)과 딸림음(솔=4.5)이 가장 높고, 반음계 밖 음(레#, 파#, 라#)이 가장 낮다 — 장조 화성에서 실제로 그 음들이 그렇게 쓰이기 때문이다. 단조는 3번째 칸(단3도, "미"에 해당하는 자리)이 장조보다 높게 잡혀 있어서, 장조/단조를 가르는 핵심 단서가 된다.

### 24개 조성 후보와 상관계수(correlation)

C 기준으로 만들어진 이 프로파일을 그대로 D장조에 쓸 순 없으니, 12번 회전시켜서 "각 으뜸음 기준 장조 프로파일" 12개 + "단조 프로파일" 12개, 총 24개 후보를 만든다. 그리고 내가 만든 pitch-class 히스토그램이 이 24개 중 어떤 것과 **모양이 가장 비슷한지**를 피어슨 상관계수(Pearson correlation)로 잰다. 상관계수는 절댓값 크기가 아니라 "패턴의 모양"만 비교하기 때문에(크기 변화·이동에 영향받지 않음), 사람이 크게 부르든 작게 부르든, 길게 부르든 짧게 부르든 상관없이 일관되게 비교할 수 있다. 상관계수가 가장 높은 후보가 정답 조성이다.

### confidence는 왜 "1위 상관계수"가 아니라 "1위-2위 차이"인가

상관계수 자체가 높아도(예: 0.9) 2위 후보도 거의 비슷하게 높으면(0.89) 사실 애매한 상황이다 — 흔한 예로 다장조(C Major)와 그 관계단조인 가단조(A Minor)는 쓰는 음이 완전히 같아서 상관계수가 서로 아주 가깝게 나온다. 그래서 "얼마나 확실한가"는 1위 값 자체보다 **1위와 2위의 격차(margin)**로 판단했다. PRD의 "조성이 모호하면 재녹음을 안내한다" 요구사항을 상위 로직(UI)에서 처리할 때 이 confidence 값을 기준으로 쓰면 된다.

### 왜 여기서 재녹음 안내 로직을 넣지 않았나

`KeyDetector`는 confidence 수치만 계산해서 반환하고, "얼마나 낮으면 재녹음을 안내할지"는 판단하지 않는다. 임계값 정책은 UI/사용자 경험 결정이라 신호처리 로직과 분리해뒀다 — 나중에 실제 데이터로 임계값을 튜닝할 때 이 함수를 건드릴 필요가 없다.

## 9. ChordGenerator — diatonic 3도/5도 화음 생성

### "3도 위"는 반음 개수가 아니라 음계 칸 수

음악에서 "3도"는 반음을 몇 개 세는 게 아니라 **음계 상에서 몇 번째 음인가**를 센다. C장조에서 C의 3도 위는 E(반음 4개 = 장3도)지만, D장조에서 D의 3도 위는 F#(반음 4개 = 역시 장3도, 하지만 흰 건반이 아니라 검은 건반)이다. 그런데 같은 장조라도 시작음에 따라 장3도/단3도가 자동으로 섞인다 — 예를 들어 C장조에서 D 위의 3도는 F(반음 3개 = 단3도)다. `ChordGenerator`가 반음을 직접 세지 않고 **"음계 배열에서 인덱스를 2칸/4칸 이동"** 하는 방식을 쓴 이유가 이것이다 — 이렇게 하면 장3도/단3도를 조성에 맞게 자동으로 올바르게 골라준다("diatonic 화성"의 핵심).

- 3도 위 = 음계 인덱스로 2칸 이동 (예: 인덱스 0인 도 → 인덱스 2인 미)
- 5도 위 = 음계 인덱스로 4칸 이동 (도 → 인덱스 4인 솔)

### MIDI 노트 번호로 계산하는 이유

`KeyDetector`처럼 pitch class(0~11, 옥타브 무관)만으로는 화음을 못 만든다 — "3도 위"가 실제로 몇 Hz인지 알려면 옥타브까지 포함한 절대 음높이(MIDI 노트 번호, 예: C4=60)가 필요하다. `NoteNameConverter`에서 Hz↔MIDI 변환 공식을 재사용 가능한 함수(`exactMIDINote(forFrequency:)`, `frequency(forMIDINote:)`)로 뽑아내서, 여기서 그대로 가져다 쓴다 — 같은 공식(69 + 12·log2(f/440))을 두 파일에 따로 베끼지 않기 위함.

### "항상 멜로디 위로 쌓기" 옥타브 보정

음계 인덱스로 목표 음이름을 찾으면, 그 음이 멜로디와 같은 옥타브 안에서는 멜로디보다 **낮은 자리**에 있을 수도 있다 (예: G4 위의 5도인 D는 같은 옥타브에서 D4=62로 G4=67보다 낮다). "3도 위/5도 위"라는 요구사항상 화음은 항상 멜로디보다 높아야 하므로, 이런 경우 한 옥타브(12 반음)를 더해서 D5(74)로 올린다. 이건 실제 합창/중창에서 위 화음을 붙일 때 자연스러운 보이싱과도 일치한다.

### 온음계에 없는 음(반음계 경과음)은 왜 nil을 반환하나

사용자가 판별된 조성의 온음계 밖의 음(예: C장조에서 C#)을 불렀다면, 그 음 위에 "온음계적으로 올바른" 3도/5도가 정의되지 않는다(반음계 화성은 v1 범위 밖). 억지로 가장 가까운 음계 음으로 스냅하는 대신 nil을 반환해서, 이런 경우를 어떻게 처리할지(무시할지, 반음계 화성으로 확장할지)는 나중에 상위 로직에서 명시적으로 결정하게 열어뒀다.

## 10. MelodySession — 마이크 파이프라인과 KeyDetector/ChordGenerator 연결

### "프레임 단위 결과"를 "조성 판별용 입력"으로 바꾸는 접착제

`KeyDetector`는 "pitch class별로 총 얼마나 오래 냈는가"라는 누적된 통계를 원하는데, `AudioCapture`는 ~46ms짜리 프레임 하나하나에 대해 콜백을 부른다. `MelodySession`은 이 둘 사이를 잇는다 — 매 프레임이 들어올 때마다 "이 프레임 길이(frameDuration)만큼 이 pitch class에 더한다"를 반복해서, 자연스럽게 "길이 가중치가 반영된 pitch-class 히스토그램"을 쌓는다. 온셋/오프셋(음이 언제 시작하고 끝나는지)을 따로 검출하지 않고도, 프레임 단위 누적만으로 근사가 되는 셈이다 — 정교하지는 않지만 프로토타입 단계에서는 충분하다.

### 왜 클래스(참조 타입)로 만들었나

`KeyDetector`, `ChordGenerator`와 달리 `MelodySession`은 `enum`이 아니라 `final class`다. 이 컴포넌트는 "지금까지 부른 멜로디"라는 **상태**를 세션 내내 유지해야 하기 때문이다(사용자가 "다시 시작"을 누르기 전까지 계속 쌓임). `AudioCapture`와 같은 이유로 순수 함수가 아니라 상태를 가진 I/O 인접 컴포넌트로 분류했다 — 다만 실제 "판단"(조성이 뭔지, 화음이 뭔지)은 여전히 `KeyDetector`/`ChordGenerator`라는 순수 함수에 그대로 위임하고, 이 클래스는 상태 누적과 그 상태를 순수 함수 입력 형태로 변환하는 역할만 한다.

### 무음 프레임(nil)을 무시하는 이유

VAD가 걸러낸 무음 프레임까지 pitch class 0(C)처럼 취급해서 누적하면 조성 판별이 완전히 틀어진다. `record(_:)`가 `nil`을 받으면 아무 것도 하지 않고 조용히 넘어가도록 만들어서, 이 문제를 원천 차단했다.

### 화면에 보이는 값의 의미

- **조성**: 지금까지 부른 멜로디 전체의 누적 통계 기준 — 노래를 더 부를수록 계속 갱신되고, 보통 더 안정적으로 수렴한다.
- **화음 제안**: 그 조성을 기준으로 "마지막으로 부른 한 음" 위에 3도/5도를 쌓은 것 — 매 프레임 바뀔 수 있다(멜로디가 계속 움직이므로).

## 11. TonePlayer — 화음 목표음 재생 (Phase 3 착수)

### 왜 필요한가

`ChordGenerator`가 "E4, G4"라는 화음을 제안해도, 그게 실제로 맞는 제안인지 텍스트만 봐서는 알기 어렵다. 가장 직접적인 검증 방법은 **그 소리를 실제로 들어보는 것**이다. `TonePlayer`는 지정한 주파수의 순수 사인파(배음이 없는 가장 단순한 파형)를 계속 재생해서, 방금 부른 멜로디와 제안된 화음이 실제로 귀에 어울리는지 바로 확인할 수 있게 한다. Phase 3의 "목표음 재생" 요구사항의 첫걸음이자, 나중에 "이 목표음을 따라 불러보세요" 훈련의 기준음으로도 그대로 재사용된다.

### AVAudioSourceNode — 코드로 직접 소리를 "생성"하기

지금까지 오디오는 항상 마이크에서 "들어오는" 쪽만 다뤘다(`AVAudioEngine.inputNode`). `TonePlayer`는 반대로 오디오를 "만들어서 내보내는" 쪽이다. `AVAudioSourceNode`는 오디오 엔진이 매 프레임마다 스피커로 내보낼 샘플이 필요할 때 호출하는 콜백을 등록하는 노드다 — 이 콜백 안에서 사인 함수 값을 계산해 버퍼를 채워 넣으면, 그게 그대로 소리가 되어 나간다.

```swift
sample = sin(phase) * amplitude
phase += 2π × frequency / sampleRate   // 매 샘플마다 위상을 이만큼 전진시킨다
```
`phase`(위상)가 한 바퀴(2π) 도는 데 걸리는 샘플 수가 정확히 `sampleRate / frequency`가 되도록 맞춘 것 — 이게 바로 "주파수"의 정의(초당 반복 횟수)를 코드로 옮긴 것이다.

### 그래프를 한 번만 만드는 이유 — 소리가 겹쳐 쌓이는 버그

처음 구현에서는 재생 버튼을 누를 때마다 새 `AVAudioSourceNode`를 만들어 엔진에 붙였는데, 이러면 이전에 붙였던 노드가 엔진 그래프에서 제거되지 않은 채 남아있어서 **재생을 반복할수록 오래된 톤들이 겹쳐서 계속 들리는** 문제가 생긴다. 그래서 노드 연결(그래프 구성)은 최초 1번만 하고, 이후 재생/정지는 `engine.start()`/`engine.pause()`로 오디오 엔진 자체를 멈췄다 재개하는 방식으로 바꿨다 — 그래프는 그대로 두고 "흐르게 할지 말지"만 켜고 끄는 것.

### `.playAndRecord`로 카테고리를 바꾼 이유와 트레이드오프

지금까지는 `.record`(녹음 전용) 카테고리를 썼는데, 이제 마이크로 듣는 동시에 스피커로 소리를 내야 하므로 `.playAndRecord`로 바꿨다. 문제는 **스피커로 나간 소리가 다시 마이크로 들어가 섞일 수 있다**는 점이다(음향학적 피드백/에코) — 통화 앱들은 이걸 막으려고 AEC(음향 반향 제거) 처리를 쓰는데, 우리는 `.measurement` 모드를 쓰는 한 그런 처리가 최소화되어 있어서 이 문제에 더 취약하다. 재생 볼륨을 낮게 잡아서 완화하는 방법도 있지만, 실기기에서 테스트해보니 너무 안 들려서(0.15 -> 0.6) 오히려 키웠다 — 근본적으로는 이어폰/헤드폰 사용을 권장하거나, "듣기"와 "부르기"를 완전히 분리된 단계로 나누는 UX가 더 안전하다. Phase 3 UI를 다듬을 때 다시 고려할 지점.

### 화음의 음을 하나씩 순서대로 들려주는 이유

처음엔 3도 음 하나만 계속 재생했는데, "화음이 맞는지 확인"하려면 3도와 5도를 각각 따로 들어봐야 판단하기 쉽다(두 음을 동시에 섞어 재생하면 초보자 귀에는 구분이 잘 안 된다). 그래서 `ContentView.playHarmonyNotesInSequence()`가 화음 배열을 한 음씩(0.8초씩) 순환 재생하도록 바꿨다. 이 루프는 매 바퀴마다 `melodySession.suggestedHarmony`를 다시 읽기 때문에, 재생 중에 계속 노래를 이어 부르면 다음 바퀴부터 최신 화음을 자동으로 반영한다 — 즉 "지금까지 부른 멜로디에 실시간으로 맞는 화음"을 계속 따라간다. (파일로 녹음된 멜로디를 입력하는 기능은 아직 없다 — 지금은 마이크 실시간 입력만 지원하고, 파일 입력은 PRD에서 Could-have로 남겨둔 v2 스코프다.)

### 재생 루프와 프레임 콜백이 동시에 주파수를 건드리면 안 되는 이유

전에는 마이크 콜백 안에서 "재생 중이면 최신 3도로 주파수를 갱신"하는 코드가 있었는데, 이제 재생 루프(`playHarmonyNotesInSequence`)가 자기 페이스(0.8초마다)로 주파수를 갱신하는 역할을 전담하므로 이 코드를 지웠다. 두 곳에서 동시에 `tonePlayer.setFrequency()`를 부르면 어느 쪽이 마지막에 이겼는지에 따라 음이 매 프레임(46ms)마다 널뛰듯 바뀌어서 화음처럼 안 들리고 지저분하게 흔들리는 소리가 났을 것이다.

### 스피커 소리가 마이크로 되먹임되는 피드백 루프 — 실제로 터진 버그

`.playAndRecord` 카테고리로 바꾸면서 우려했던 문제(위 항목)가 실제로 발생했다: 화음을 재생하면 그 소리가 마이크로 다시 들어가서 `YINPitchDetector`가 "새로 부른 음"으로 감지하고, `MelodySession`이 그걸 `lastNote`로 기록한 뒤, 그 음 위에 또 새 화음을 제안하고, `TonePlayer`가 그 새 화음을 재생하고... 이런 식으로 **재생 → 재인식 → 새 제안 → 재생**이 꼬리를 물고 이어지는 피드백 루프가 생겼다. 사용자 입장에서는 버튼 한 번 눌렀는데 화음이 계속 다른 음으로 바뀌는 것처럼 보였다.

해결: 재생 중(`isPlayingTone == true`)에는 마이크 콜백 맨 앞에서 즉시 `return`해서 `MelodySession.record()` 자체를 호출하지 않는다 — 재생 중엔 마이크 입력을 통째로 무시하는 것. 그리고 재생할 화음은 버튼을 누른 시점에 `melodySession.suggestedHarmony`를 한 번만 읽어서 지역 변수(`lockedHarmony`)로 고정한 뒤, 재생 루프는 그 고정된 배열만 반복 재생한다 — 매 바퀴 다시 읽지 않는다. 이렇게 하면 "다시 시작을 누르기 전까지는 이 음에 대한 화음만 듣는다"는 사용자 기대와 정확히 일치하고, 재생 중 들어온(사실은 스피커에서 나간) 소리가 `MelodySession`의 누적 통계를 오염시키는 것도 막는다.

## 12. PitchScorer + 콜앤리스폰스 채점 — Phase 3 실시간 채점

### 3도/5도를 각각 채점하기

처음엔 "채점 시작" 버튼 하나가 항상 3도만 목표로 삼았는데, 화음은 3도와 5도 두 음으로 이뤄지니 둘 다 연습할 수 있어야 한다. 그래서 버튼을 "3도 채점" / "5도 채점" 두 개로 나누고, `toggleScoring(interval:)`이 `ChordGenerator.HarmonyNote` 배열에서 해당 interval을 찾아 목표로 고정하도록 바꿨다. 채점 중에 반대쪽 버튼을 누르면 멈췄다 다시 시작하는 게 아니라 **바로 목표를 전환**한다 — 3도/5도를 번갈아 연습할 때 매번 중지 버튼을 따로 누르는 불편을 없애기 위함. 목표가 바뀔 때마다 `pitchSmoother.reset()`도 같이 호출해서, 이전 목표음 근처에서 쌓인 스무딩 값이 새 목표 채점에 섞여 들어가지 않게 한다.

### 왜 "재생하면서 동시에 채점"하지 않았나

PRD가 그리는 이상적인 그림은 "목표 화음이 계속 울리는 동안 그걸 들으며 따라 부르고, 편차가 실시간으로 표시되는" 것이다. 하지만 지금 구조(스피커+마이크를 동시에 쓰고 AEC 없는 `.measurement` 모드)에서는 목표음을 재생하면서 동시에 마이크로 사용자 목소리만 깨끗이 구분해 듣는 게 사실상 불가능하다 — 방금 11절에서 겪은 피드백 루프가 바로 그 증거다. 그래서 이번 프로토타입은 **콜앤리스폰스(call-and-response)** 방식으로 스코프를 좁혔다: (1) 목표음을 듣는다 → (2) 재생이 멈추면 마이크가 다시 켜진다 → (3) 그 목표음을 기억하며 따라 부르면 실시간으로 채점된다. 동시 재생+채점은 나중에 이어폰 전제, 또는 AEC가 있는 다른 오디오 세션 모드를 조사한 뒤 다시 시도해볼 만한 확장 지점으로 남겨둔다.

### PitchScorer가 NoteNameConverter와 다른 점

`NoteNameConverter.centsOffset`은 "가장 가까운 평균율 음(12개 중 하나)"과의 차이를 잰다. 반면 `PitchScorer`는 그 12개 중 하나가 아니라 **임의의 목표 주파수 하나**(예: 화음의 3도 음, 정확히는 391.995...Hz 같은 값)와의 차이를 잰다. 계산식은 똑같이 `1200 × log2(비율)`(cent는 정의상 반음의 1/100이고, 반음 하나는 주파수비 2^(1/12)이므로, 두 주파수의 비율에 로그를 취해 반음 단위로 환산한 뒤 100을 곱한 것)이지만, 비교 대상이 "고정된 평균율 격자"냐 "임의의 목표음 하나"냐가 다르다.

### 허용 오차(±35 cent)는 왜 그 값인가

100 cent가 반음 하나이므로, 35 cent는 반음의 1/3 조금 넘는 정도다. 이 값은 엄밀한 근거보다는 "너무 빡빡하면 초보자는 다 틀렸다고 나오고, 너무 널널하면 반음 옆 음도 맞았다고 나오는" 균형점을 잡은 시작값이다 — 실제 사용자 테스트를 거쳐 조정이 필요한 값이라는 걸 코드 주석에도 남겨뒀다.

### UI를 "번호가 붙은 단계"로 재구성한 이유

지금까지는 상태 텍스트와 버튼들이 그냥 세로로 나열돼 있어서, 화면만 보고는 "이게 지금 파이프라인의 어느 단계인지" 알기 어려웠다. `ContentView`를 1.실시간 피치 → 2.조성 판별 → 3.화음 제안 → 4.따라 부르기 채점, 이렇게 번호 붙은 섹션(`flowSection`)으로 나눠서, 화면 구조 자체가 `AudioCapture → KeyDetector → ChordGenerator/TonePlayer → PitchScorer`로 이어지는 실제 데이터 흐름과 그대로 대응되게 했다. 디자인을 다듬은 건 아니고, "지금 무슨 일이 일어나고 있는지"를 한눈에 보이게 하는 최소한의 정리다.

### PitchMeterView — 숫자 대신 바늘로 보여주기

`%+.0f cent`처럼 텍스트로 숫자를 보여주면, "지금 내가 높게 부르고 있는지 낮게 부르고 있는지"를 머릿속으로 다시 해석해야 한다. 기타 튜너 앱들이 전부 바늘/막대 형태의 시각적 미터를 쓰는 이유가 이거다 — 왼쪽/오른쪽이라는 공간적 위치가 "낮음/높음"이라는 의미와 자연스럽게 대응돼서 해석 과정이 필요 없다.

- **가로 위치 매핑**: `cents / displayRangeCents`(±50cent를 화면 폭 전체로 잡음) 비율을 계산해서 중앙(0cent)을 기준으로 좌우로 이동시킨다. ±35cent보다 넓은 ±50cent를 표시 범위로 잡은 이유는, 허용오차 범위(±35)만 딱 맞춰 잡으면 조금만 벗어나도 바늘이 화면 끝까지 튀어서 "얼마나" 벗어났는지 구분이 안 되기 때문이다.
- **허용오차 구간 음영**: `PitchScorer.onPitchToleranceCents`(±35cent)에 해당하는 폭만큼 중앙에 초록색 음영을 깔아서, 바늘이 그 구간 안에 들어오면 "정확" 판정이라는 걸 굳이 텍스트를 안 봐도 알 수 있게 했다.
- **clamp 처리**: 표시 범위(±50cent)를 벗어나는 극단적인 편차는 막대 끝에 붙여서(clamp) 보여준다 — 튜너 앱들도 대부분 이렇게 하는데, 안 그러면 옥타브 단위로 완전히 다른 음을 불렀을 때 바늘이 미터 밖으로 나가버려서 UI가 깨진 것처럼 보인다.

## 13. PitchSmoother — 비브라토로 튀는 값을 눌러주기

### 왜 필요했나

바늘 미터를 실기기에서 써보니 "음이 샵도 되고 플랫도 나고 막 흔들린다"는 문제가 있었다. 이건 버그가 아니라 **사람 목소리의 본질적인 특성**이다 — 아무리 안정적으로 부르려 해도 성대는 초당 몇 번씩 미세하게 떨리고(비브라토), 음을 처음 낼 때는 정확한 피치에 안착하기까지 약간의 시간이 걸린다(온셋 불안정). YIN은 이걸 있는 그대로, 프레임(약 46ms)마다 정직하게 측정해서 보여주기 때문에 원본 값 그대로는 미터가 지저분하게 떨린다. PRD 부록 B에도 "비브라토는 프레임 단위 편차의 이동평균으로 스무딩" 이라고 이미 이 보완책이 예정되어 있었다.

### 왜 Hz가 아니라 MIDI 노트(로그 스케일)에서 평균을 내나

`NoteNameConverter`에서 다뤘듯 피치는 로그적으로 지각된다. 만약 411Hz와 466Hz(반음 차이가 다른 두 저음역 예시)를 그냥 Hz 단위로 평균 내면, 저음역과 고음역에서 "같은 반음 차이"가 평균 계산에 서로 다른 영향을 준다. MIDI 노트 번호로 변환한 뒤 평균을 내면(그리고 다시 Hz로 변환하면), 음역대에 상관없이 일관된 스무딩이 된다.

### 지수이동평균(EMA)이 하는 일

```
새 평균값 = 이전 평균값 + factor × (이번 측정값 - 이전 평균값)
```
`factor`(0.3)가 클수록 최신 값에 더 민감하게 반응하고(반응은 빠르지만 덜 부드러움), 작을수록 여러 프레임에 걸쳐 더 부드럽게 움직인다(부드럽지만 반응이 느려짐). 매 프레임 전체 이력을 저장하지 않고 "이전 평균값 하나"만 기억하면 되기 때문에, 이동평균(moving average)보다 구현이 간단하고 메모리도 적게 쓴다 — 그래서 실시간 오디오 처리에서 자주 쓰인다.

### 어디에 적용했고, 어디엔 안 했나

1단계(실시간 피치) 표시는 원본 값을 그대로 보여준다 — Phase 1의 "검출된 주파수를 있는 그대로 보여준다"는 요구사항, 그리고 디버깅 시 원본 신호를 확인할 수 있어야 한다는 이유 때문이다. 반면 4단계(채점)에서 `PitchScorer`에 넘기는 값은 스무딩을 거친다 — 채점의 목적은 "지금 대충 맞는 음을 내고 있는지"를 판단하는 것이라, 순간적인 흔들림보다 안정된 경향이 더 중요하기 때문이다.

## 14. 단음 캡처 모드 — "일단 한 음만" 고정하기

### 왜 필요했나

`MelodySession`은 원래 "계속 부르는 멜로디 전체"를 누적하도록 설계했는데, 지금 단계에서 실제로 마이크에 들어오는 건 숨소리, 다음 음절, 주변 잡음 등 온갖 소리가 섞여 있다. 매 프레임 `lastNote`가 갱신되니, 사용자가 의도한 것과 무관하게 조성·화음이 계속 바뀌었다 — "지금은 단음으로만, 음 하나가 들어가면 그 음에 맞는 화음이 고정돼야 한다"는 사용자 피드백대로, 나중에 곡 전체를 듣고 여러 화음을 뽑아내는 기능(진짜 `MelodySession`의 원래 목적)과는 별개로, 지금은 "한 음만 잡아서 고정"하는 게 필요했다.

### 스트릭(streak) 확정 — 잡음 한 프레임에 안 속기

VAD를 통과했다고 다 "진짜 노래하는 음"은 아니다 — "음"이나 "스" 같은 자음의 순간적 파열음도 짧게는 YIN에 걸릴 수 있다. 그래서 pitch class(옥타브 무관 음이름)가 **연속으로 3프레임(약 140ms) 같은 값**을 유지해야만 그 음으로 확정한다. 1프레임(46ms)이면 순간적인 잡음일 수도 있지만, 140ms 동안 같은 음이 유지된다는 건 실제로 그 음을 내고 있다는 뜻에 가깝다.

## 15. PracticeAttempt + SwiftData — 세션 종료 후 정확도 요약

### 프레임을 그대로 저장하지 않는 이유

채점(`PitchScorer`)은 프레임(약 46ms)마다 결과를 낸다 — 몇 초만 따라 불러도 수십 개의 점수가 쌓인다. 이걸 전부 SwiftData에 저장하면 기기 저장공간만 낭비하고, 나중에 "지난번에 어땠지"를 볼 때도 원시 데이터 수십 개를 다시 계산해야 한다. 그래서 채점 시도 하나(3도를 몇 초간 따라 부른 것, 혹은 5도로 바꾸기 전까지)가 끝나는 시점에 `PracticeSummary.aggregate(scores:)`로 **하나의 요약 통계**(샘플 개수, 정확 판정 비율, 평균 편차 크기)로 압축한 뒤, 그 요약 하나만 `PracticeAttempt`로 저장한다.

### "시도가 끝나는 시점"은 언제인가

세 가지 경우 모두 `finalizeCurrentAttempt()`를 호출한다:
1. 같은 interval 버튼을 다시 눌러 채점을 끌 때
2. 채점 중에 반대쪽(3도↔5도) 버튼을 눌러 목표를 바꿀 때 — 이전 목표에 대한 시도가 여기서 끝나는 것으로 본다
3. "다시 시작"을 누를 때 — 리셋 직전까지의 시도도 버리지 않고 기록으로 남긴다

### SwiftData 최소 사용법

`@Model` 매크로를 붙인 클래스(`PracticeAttempt`)가 곧 저장 가능한 데이터 모델이다. `HarmonyUpApp`에 `.modelContainer(for: PracticeAttempt.self)`를 붙이면 앱 전체에서 이 모델을 저장/조회할 수 있는 컨테이너가 만들어진다. `ContentView`에서는 `@Environment(\.modelContext)`로 "저장할 때 쓰는 손잡이"를, `@Query(sort: \.date, order: .reverse)`로 "최신순으로 자동 정렬된 전체 기록"을 가져온다 — `@Query`는 SwiftUI의 `@State`처럼 값이 바뀌면(새 기록이 저장되면) 화면을 자동으로 다시 그려준다.

### 조성 판별(KeyDetector)과 닮은 패턴 — "자주 벗어난 화음 유형" 찾기

3도 시도들의 평균 정확도와 5도 시도들의 평균 정확도를 각각 구해서, 그 차이가 10%p 이상 나면 "OO 화음에서 더 자주 벗어나는 편"이라고 알려준다. 이건 PRD 페르소나 시나리오에서 그렸던 "세션 리포트에서 자주 벗어났던 화음 유형(5도 화음에서 정확도가 낮음)을 확인한다"는 장면을 가장 단순한 형태로 구현한 것이다 — 통계적으로 엄밀한 검정은 아니고, 눈에 띄게 차이가 날 때만 언급하는 실용적인 임계값이다.

## 16. 멜로디 모드 — 단음 모드를 원래 설계로 확장하기

### 단음 모드와 무엇이 다른가

단음 모드는 "한 음만 잡고 고정"이었다. 멜로디 모드는 `MelodySession`이 원래 하려던 일 — 곡 전체를 부르면 음마다 화음을 순서대로 받는 것 — 을 되살린 것이다. 두 모드는 캡처 로직의 **가드 조건 하나**만 다르다:

- 단음 모드: `!hasCapturedNote` — 한 번 잡으면 다시 안 잡는다.
- 멜로디 모드: 이 가드가 아예 없다 — 계속 새 음을 잡을 수 있어야 한다.

대신 멜로디 모드에는 "직전에 잡은 음과 같은 음을 계속 홀드하는 것"과 "다음 음으로 넘어간 것"을 구분하는 별도 장치(`lastCapturedPitchClass`)가 필요하다 — 안 그러면 한 음을 길게 부를 때마다 스트릭 확정 조건(3프레임 유지)을 만족할 때마다 계속 같은 음을 중복으로 쌓게 된다.

### 왜 각 스텝의 화음이 "그 순간의 조성"을 기준으로 하는가

`KeyDetector`는 지금까지 부른 음 전체의 누적 통계로 조성을 판별한다. 그런데 화면에 표시되는 각 스텝(음)의 화음은 **그 음을 확정한 시점**의 조성 판정을 그대로 쓴다. 즉 곡 초반에는 조성이 아직 불확실한 상태(음 1~2개만으로 판정)라서 화음이 부정확할 수 있고, 뒤로 갈수록 조성이 더 안정적으로 수렴하면서 화음도 더 믿을 만해진다. 엄밀하게 하려면 "노래가 다 끝난 뒤 최종 조성으로 모든 스텝의 화음을 다시 계산"하는 방식(배치 처리)이 맞겠지만, 지금은 실시간성을 유지하는 쪽을 택했다 — 프로토타입 단계에서 이 트레이드오프는 알려진 한계로 남겨둔다.

### 온음계 밖 음은 어떻게 보이나

`ChordGenerator.generateHarmony`가 nil을 반환하면(그 순간 조성의 온음계에 없는 음을 불렀을 때) 화면에는 "온음계 밖"이라고 표시한다 — 반음계 경과음을 부르면 화음을 못 붙인다는 걸 숨기지 않고 그대로 보여준다.

### 측정 시작을 버튼으로 분리하기

원래는 화면이 뜨자마자(`onAppear`) 바로 마이크를 켰다. 이러면 사용자가 준비되기 전부터 마이크가 소리를 듣고 있어서, 앱을 켜자마자 뭔가 잡히거나(주변 잡음), 정작 부르려던 타이밍보다 먼저 켜져서 첫 소절을 놓치는 문제가 있었다. "측정 시작" 버튼을 눌러야만 `AudioCapture.start()`가 호출되게 바꿔서, 사용자가 준비된 시점에 정확히 캡처가 시작되게 했다.

`AudioCapture`는 `stop()`으로 탭을 제거하고 엔진을 멈춘 뒤 `start()`를 다시 불러도 안전하게 재사용되도록 이미 설계돼 있었다(탭을 새로 걸고 엔진을 다시 준비/시작) — 그래서 버튼을 여러 번 눌러 껐다 켰다 해도 별도 예외 처리 없이 그대로 동작한다.

## 17. 멜로디 스텝 수동 수정 — 오검출을 사용자가 직접 고치기

### 왜 필요한가

YIN이 아무리 잘 튜닝돼도 실시간 피치 검출은 100% 정확할 수 없다 — 발음이나 잡음 때문에 반음 옆 음(예: G3를 F#3로)으로 잘못 잡히는 경우가 있다. 이걸 그대로 두면 조성 판별과 화음이 전부 그 오검출 위에서 계산되므로, 사용자가 "이 음은 사실 G3였어"라고 직접 정정할 수 있는 통로가 필요했다.

### MelodySession을 "누적 합계"에서 "개별 기록 배열"로 바꾼 이유

이전 구현은 pitch class별 누적 길이(12칸 배열)만 들고 있어서 "몇 번째로 잡은 음"이라는 개념 자체가 없었다 — 한 번 합쳐지면 되돌릴 수 없었다. 그래서 `RecordedNote` 배열로 바꿔서 잡은 음을 순서대로 남겨두게 했다. `KeyDetector.detectKey`는 원래도 같은 pitch class가 여러 번 들어와도 내부에서 알아서 더하기 때문에(3절 참고), 배열로 바꿔도 조성 판별 결과 자체는 똑같이 나온다 — 그러면서 "인덱스로 특정 음만 골라 고치기"가 가능해졌다.

### 옥타브는 그대로 두고 pitch class만 바꾸는 이유

수정 UI는 12개 음이름(C~B) 중에서 고르게 했지, 옥타브까지 다시 고르게 하지 않았다. YIN의 흔한 오검출 패턴은 반음 옆으로 잘못 잡는 것이지 옥타브를 통째로 잘못 잡는 경우는 상대적으로 드물고(Phase 1에서 이미 검증됨), 사용자가 예로 든 "F#3 → G3"도 같은 옥타브 안에서의 수정이었다. `newMIDINote = oldMIDINote - oldMIDINote.mod(12) + newPitchClass`로 옥타브(정수 나눗셈으로 결정되는 부분)는 유지하고 반음 자리만 바꾼다.

### 수정 하나가 전체 시퀀스에 영향을 주는 이유

한 음을 고치면 `MelodySession`에 누적된 pitch-class 분포가 바뀌고, 그러면 `detectedKey`(조성 판별 결과)도 달라질 수 있다. 조성이 바뀌면 그 조성을 기준으로 만들어졌던 다른 스텝들의 화음도 더 이상 맞지 않는다. 그래서 수정이 일어나면 화면에 있는 **모든** 스텝의 화음을 새 조성 기준으로 다시 계산한다 — 한 스텝만 고치고 나머지는 예전 조성 그대로 두면, 같은 화면 안에 서로 다른 조성 가정이 섞여서 더 헷갈리게 된다.

### 마지막 음을 고쳤을 때만 `lastNote`를 갱신하는 이유

`MelodySession.suggestedHarmony`(화음 듣기/채점의 기준)는 `lastNote`(가장 최근에 부른 음) 위에 화음을 쌓는다. 중간에 있는 스텝을 고쳐도 "지금 채점하려는 목표음"은 여전히 마지막 음이어야 맞다 — 그래서 `correctNote(at:to:)`는 고친 인덱스가 배열의 마지막일 때만 `lastNote`도 같이 바꾼다.

## 18. 멜로디 모드에서 채점이 먹통이었던 버그

### 증상과 원인

멜로디 모드에서 "3도 채점"을 누르고 목표음을 따라 불렀는데 바늘이 안 움직이는 문제가 있었다. 원인은 멜로디 모드가 애초에 "음이 바뀔 때마다 계속 새로 잡아야" 하도록 만들어져 있어서(16절), **채점하려고 목표음을 따라 부르는 것 자체가 새 멜로디 음으로 잡혀버렸다**. 그러면:

1. `melodySession`에 그 음이 새로 기록되면서 `lastNote`가 바뀌고
2. `detectedKey`(조성)도 다시 계산되고
3. 그 결과 `suggestedHarmony`가 갑자기 `nil`이 될 수 있다(방금 부른 음이 새로 계산된 조성의 온음계 밖일 때)
4. "3도 채점"/"5도 채점" 버튼은 `melodySession.suggestedHarmony == nil`이면 비활성화되므로, 버튼을 눌러도 조용히 아무 일도 안 일어나거나(guard에서 조기 반환) 채점 상태가 불안정해진다

채점 자체(`PitchScorer.score`)는 항상 고정된 `scoringTarget`과 실시간 주파수를 비교하는 순수 계산이라 버그가 없었다 — 문제는 "채점을 시작할 조건을 만드는 배경(melodySession)이 채점 도중에도 계속 흔들렸다"는 것이었다.

### 해결: 채점 중엔 멜로디 캡처를 멈춘다

`shouldEvaluateCapture`(새 멜로디 음을 잡을지 말지 결정하는 조건)에 `scoringTarget == nil`을 추가했다. 즉 채점 중(목표음이 정해져 있는 동안)에는 멜로디 모드라도 새 음을 잡지 않는다 — 화음 재생 중에 마이크를 무시하는 것과 같은 패턴이다(11절). 이렇게 하면 채점이 진행되는 동안 `melodySession`이 그대로 얼어붙어 있어서, `scoringTarget`이 가리키는 화음이 채점 내내 안정적으로 유지된다.

## 19. 채점을 3도/5도 각각 독립적으로 — 상태를 Dictionary로 관리하기

### 왜 하나의 상태로는 부족했나

이전엔 `scoringTarget`/`currentScore` 같은 단일 변수 하나로 "지금 채점 중인 것"을 표현했다. 그러다 보니 3도를 채점하다 5도로 넘어가면 3도의 결과가 그대로 덮어써져 사라졌다 — 세션 기록(5단계)엔 남지만, 화면에서 "3도는 지금 어느 정도 되고 있었지"를 바로 다시 볼 수는 없었다.

### interval을 키로 쓰는 Dictionary로 바꾸기

`activeScoringInterval`(지금 실제로 마이크가 채점하고 있는 대상, 하나뿐)과 `latestScores`/`lockedScoringTargets`/`scoreSampleBuffers`(3도·5도 각각의 결과를 따로 담는 `[Interval: T]` Dictionary)를 분리했다. 이렇게 하면:
- 지금 마이크가 실제로 판단할 수 있는 건 한 번에 하나(사람은 한 번에 한 음만 부르니까)지만
- 화면에는 3도 패널과 5도 패널이 각자의 최신 결과를 계속 들고 있다가 보여준다

`ChordGenerator.Interval`을 Dictionary 키로 쓰려면 `Hashable`이어야 해서, 기존 `Equatable` 선언을 `Hashable`로 바꿨다(연관값 없는 단순 enum이라 자동 합성됨).

### 채점 버튼이 측정을 직접 켜도록 만들기

이전엔 "측정 시작"을 먼저 눌러야만 채점이 동작했다 — 측정을 꺼둔 채로 채점 버튼을 누르면 마이크 자체가 안 돌고 있으니 당연히 아무 반응이 없었는데, 이게 "채점이 안 된다"는 오해를 낳았다. `toggleScoring`이 `beginCapturingIfNeeded()`(측정이 꺼져 있으면 켜고, 이미 켜져 있으면 아무 것도 안 하는 멱등 함수)를 직접 호출하도록 해서, "채점하기"를 누르는 순간 측정 여부를 신경 쓰지 않아도 바로 동작하게 만들었다. 반대로 "측정 중지"를 누르면 진행 중이던 채점도 먼저 기록으로 저장하고 정리한 뒤 마이크를 끈다 — 채점이 켜진 채로 마이크만 꺼져서 아무 반응 없는 상태가 되는 걸 막기 위함.

### 멜로디 전체를 화음 라인으로 이어서 듣기

지금까지는 화음을 "한 순간의 목표음 하나"로만 다뤘다 — 단음 모드의 목표음 하나, 또는 멜로디 모드에서 스텝 하나씩. 그런데 도-미-솔처럼 멜로디를 이어 불렀다면, 그 전체에 대응하는 3도(또는 5도) 라인도 이어서 들어보고 싶다는 요청이 있었다. `melodyHarmonyLine(interval:)`이 이걸 만든다 — 저장해둔 `harmonyNames` 문자열을 재활용하는 대신, 재생하는 시점에 **매번 다시 계산**한다. 이유는 사용자가 스텝을 고쳐서(17절) 조성이 바뀌었을 수도 있는데, 그러면 오래된 문자열이 아니라 항상 최신 조성 기준으로 들려줘야 하기 때문이다.

재생 방식은 화음 듣기(단일 목표음, 끝없이 반복)와 다르게 **한 바퀴 돌면 자동으로 멈춘다** — 멜로디는 길이가 정해져 있는 시퀀스라서, 계속 반복하면 "지금 어디까지 들었지"를 알기 어렵다. 한 번 끝까지 들려주고 멈추는 게 "이 멜로디에 대응하는 화음"이라는 완결된 단위로 느껴지게 한다.

## 20. PitchShifter — 내 목소리로 화음 만들기 (WSOLA)

### 목표

지금까지 화음은 전부 `TonePlayer`의 합성음(사인파+배음)으로 들려줬다. 이번엔 사용자 목소리를 짧게 녹음해서, 그 목소리 톤 그대로 3도/5도 위로 피치만 옮겨 재생하는 기능이다 — "합성음이 아니라 내 목소리로 화음 듣기".

### 왜 "길이는 그대로, 피치만" 바꾸는 게 어려운가

녹음 재생 속도를 그냥 빠르게/느리게 하면 피치는 바뀌지만 재생 시간도 같이 바뀐다("다람쥐 소리" 효과). 길이는 그대로 두고 피치만 바꾸려면 두 단계가 필요하다:
1. **시간축 늘이기(time-stretch)**: 재생 속도(피치)는 원래대로 두고 길이만 `pitchRatio`배로 늘이거나 줄인다.
2. **리샘플링**: 그 결과를 `pitchRatio`배 빠르기로 다시 읽는다 — 리샘플링은 피치와 길이를 동시에 `pitchRatio`배 하므로, 1단계에서 미리 늘려둔 길이가 다시 원래 길이로 돌아오면서 피치만 옮겨진 결과가 나온다.

리샘플링(2단계)은 선형보간만 하면 되는 간단한 작업이라 처음부터 정확했다. 진짜 어려운 건 1단계, 피치를 그대로 유지하면서 길이만 바꾸는 시간축 늘이기(time-stretch)다.

### 1차 시도: OLA(Overlap-Add)와 그 실패

가장 단순한 방법은 원본을 짧은 조각(그레인)으로 잘라서, 조금씩 겹치게(오버랩) 다시 이어 붙이는 것이다(Overlap-Add). 그런데 그레인을 아무 위치에서나 잘라 겹치면, 겹치는 구간끼리 파형의 위상이 어긋나서 순음(sine)조차 서로 간섭해 다른 신호로 뭉개진다("phasiness") — 실제로 처음 구현에서, 순음을 넣었는데도 원래 신호와 무관한 저주파(그레인을 이어 붙이는 간격 자체의 주파수)가 검출되는 버그로 나타났다.

### 2차 시도: 영교차점 정렬 — 부분적으로만 효과

겹치는 그레인을 "위로 향하는 영교차점(zero-crossing)"에 맞춰 자르면 위상이 맞아떨어질 거라 생각했다. 순음 하나로 테스트했을 땐 그럴듯했지만, 실제 배율(비율≠1)로 조각을 이어 붙이는 상황에서는 실패했다 — 매 그레인을 "목표 위치 근처에서 아무 영교차점"이나 고르다 보니, 검색 범위가 신호의 한 주기보다 넓으면 결국 매번 "같은 위상"의 지점만 고르게 되어(주기 신호는 모든 영교차점이 똑같이 생겼으므로) 그레인들이 전부 똑같은 내용이 되어버렸다. 그 결과 역시 원래 신호가 아니라 그레인 간격 자체의 주파수가 다시 검출됐다.

### 3차 시도: WSOLA(Waveform-Similarity OLA) — 성공

영교차점 "하나"만 보는 대신, **파형 전체의 생김새**를 비교해서 가장 비슷한 지점을 찾는 방식(WSOLA)으로 바꿨다. 구체적으로, 그레인 하나를 새로 배치할 때 "직전 그레인에서 자연스럽게 이어졌다면 나왔을 파형"을 참조 삼아, 원하는 위치 근처에서 그 참조와 **내적(dot product)이 가장 큰**(=가장 비슷한 모양의) 구간을 찾는다:

```
score(candidate) = Σ reference[i] × samples[candidate + i]
```

이렇게 하면 "아무 영교차점이나" 고르는 모호함이 없어진다 — 파형 모양 자체를 비교하니, 순음이든 사람 목소리든 실제로 이전 그레인과 자연스럽게 이어지는 위치를 정확히 찾아낸다. 이 수정 후 유닛테스트(장3도 위, 완전5도 아래로 옮긴 사인파를 다시 YINPitchDetector로 검증)가 모두 통과했다.

### 이 버그를 잡은 방법 — 단계를 쪼개서 이분 탐색하듯 디버깅

"3도 위로 옮기기"가 실패했을 때, 어느 단계(시간축 늘이기 vs 리샘플링)가 문제인지 바로 알 수 없었다. 그래서 `timeStretch`와 `resample`을 각각 별도로 호출해서 검증하는 테스트를 추가했다 — "시간축만 늘였을 때 피치가 그대로 유지되는가", "리샘플링만 했을 때 피치가 정확히 배율만큼 바뀌는가"를 따로 확인하니 리샘플링은 처음부터 정확했고, 문제가 시간축 늘이기 쪽에 있다는 게 명확해졌다. 이미 만들어둔 `YINPitchDetector`가 이번엔 "내가 만든 도구가 내가 만든 다른 도구를 검증하는" 역할을 톡톡히 했다.

### 실기기 크래시 — 모노/스테레오 채널 불일치

실기기에서 "내 목소리로 3도"를 누르자 바로 앱이 튕겼다: `_outputFormat.channelCount == buffer.format.channelCount` 단언 실패. `VoiceClipPlayer`가 `AVAudioPlayerNode`를 믹서에 연결할 때 `format: nil`을 줬는데, 이러면 엔진이 믹서의 기본 포맷(보통 스테레오, 2채널)으로 연결을 확정해버린다. 그런데 실제로 재생하려는 버퍼는 마이크로 녹음한 **모노(1채널)** 오디오라서, 재생 시점에 "연결된 포맷(2채널)"과 "버퍼 포맷(1채널)"이 달라 충돌한 것이다. 시뮬레이터 유닛테스트는 `PitchShifter`의 순수 계산 결과([Float] 배열)만 검증했지 실제 `AVAudioEngine` 그래프 연결까지는 거치지 않아서 이 문제를 못 잡았다 — **오디오 엔진 그래프/포맷 관련 버그는 반드시 실기기(또는 최소한 실제 엔진을 돌려보는 것)로 확인해야 한다**는 걸 다시 확인한 사례.

고친 방법: `connect` 시점에 버퍼와 **똑같은 포맷**(모노, 실제 샘플레이트)을 명시적으로 넘겨서 애초에 불일치가 생길 수 없게 했다.

### "누른 뒤 녹음" 대신 "계속 담아뒀다가 즉시 사용" — 롤링 버퍼

처음엔 "버튼을 누르면 그 순간부터 1.2초 녹음"하는 방식이었다. 그런데 실제 사용 흐름을 생각해보면, 사용자는 보통 음을 다 부른 뒤(이미 화면에 노트가 찍힌 뒤) 그제서야 "이걸 화음으로 만들어줘" 버튼을 누른다 — 즉 **버튼을 누르는 시점엔 이미 조용해져 있는 경우가 많다.** 그 상태에서 "지금부터 1.2초"를 녹음하면 무음만 잡혀서 아무 소리도 안 나는 버그가 났다.

고친 방법은 발상을 뒤집은 것이다 — "버튼을 누른 뒤 녹음"이 아니라, **VAD를 통과하는 모든 프레임을 항상 최근 1.5초치만 유지하는 롤링 버퍼**(`recentVoiceBuffer`)에 계속 담아두고, 버튼을 누르면 그 순간까지 쌓여있던 걸 즉시 피치 시프트해서 재생한다. `recentVoiceBuffer.count > maxSamples`일 때 `removeFirst`로 오래된 앞부분을 잘라내는 식으로 "최근 N초"를 유지한다. 이렇게 하면 사용자가 방금 부른 음을 그대로 쓸 수 있어서, 버튼을 누르는 타이밍과 무관하게 항상 기대한 소리가 재생된다.

### "버튼 눌러도 반응 없음" — 여러 조건을 한꺼번에 disabled에 몰아넣은 문제

버튼의 `.disabled(...)`에 조건 4개(측정 중인지, 재생 중인지, 목소리가 잡혔는지, 화음이 있는지)를 한꺼번에 걸어뒀더니, 어느 조건 때문에 막혔는지 사용자는 알 길이 없이 그냥 "버튼이 안 눌리는" 것처럼 보였다. 특히 롤링 버퍼가 아직 안 채워진 초기 상태(`recentVoiceBuffer.isEmpty`)에서 이 조건 하나만으로 버튼 전체가 비활성화됐는데, 화면 어디에도 "왜 안 되는지"가 안 보였다.

고친 방향: **비활성화 조건은 정말 눌러도 의미 없는 최소한(측정 꺼짐, 다른 소리 재생 중)만 남기고**, 나머지(화음 없음, 목소리 안 잡힘)는 버튼을 눌렀을 때 함수 안에서 각각 확인해서 `statusText`로 이유를 알려주는 방식으로 바꿨다. 버튼이 "눌리기는 하는데 왜 안 되는지 설명해주는" 상태와 "아예 눌리지도 않는" 상태는 사용자 입장에서 완전히 다르게 느껴진다 — 항상 눌리게 해두고 이유를 말해주는 쪽이 디버깅도, 실사용도 더 낫다. 목소리가 얼마나 확보됐는지(`%.1f초`)도 화면에 항상 보이게 해서, 롤링 버퍼가 실제로 쌓이고 있는지 사용자가 직접 확인할 수 있게 했다.

### "제스처 게이트 타임아웃" — 메인 스레드에서 무거운 계산을 직접 돌린 문제

실기기 로그에 `Gesture: System gesture gate timed out.`이 반복해서 찍혔다. 이건 iOS가 "터치에 반응해야 할 화면이 일정 시간 동안 응답이 없다"고 판단할 때 나오는 시스템 로그다 — 즉 **메인 스레드가 뭔가에 붙잡혀 있다**는 신호다. 원인은 `recordAndHarmonizeVoice`가 `PitchShifter.shift(...)`(WSOLA, 그레인마다 상관관계를 계산하는 무거운 연산)를 버튼 탭 핸들러 안에서 **바로, 동기적으로** 호출하고 있었던 것 — 이 연산이 끝날 때까지 메인 스레드(=화면을 그리고 터치를 처리하는 스레드)가 통째로 멈춰버린다. 디버그 빌드는 최적화가 꺼져 있어서 이런 반복 연산이 릴리즈 빌드보다 훨씬 느리기 때문에 체감상 "버튼이 아예 안 눌리는" 것처럼 느껴졌다.

고친 방법: 무거운 계산(`PitchShifter.shift`)을 `Task { }`로 감싸서 별도로 스케줄링하고, 그 결과가 나온 뒤에만 화면 갱신과 재생을 한다. `Task { }`를 만드는 순간 함수 자체는 바로 반환되므로, 버튼 탭 핸들러가 즉시 끝나서 화면이 멈추지 않는다 — "화음 만드는 중…" 문구가 먼저 뜨고, 계산이 끝나면 재생되는 자연스러운 흐름이 된다.

### 시작음을 직접 고르게 하기

처음엔 시작음을 A4(440Hz) 하나로 고정했는데, 사람마다 부르기 편한 음역대가 다르고 곡마다 시작하고 싶은 음도 다르다. `Stepper`로 MIDI 노트 번호(`startingNoteMIDI`)를 반음 단위로 올리고 내릴 수 있게 하고, 표시되는 이름은 `NoteNameConverter`로 그때그때 변환한다 — 이미 있는 Hz↔MIDI 변환 함수를 그대로 재사용해서 새 변환 로직을 추가할 필요가 없었다. 범위는 C3~C6(MIDI 48~84)로 넉넉히 잡아서 대부분의 발성 음역대를 커버하게 했다.

### 화면 갱신을 "표시"와 "판단"으로 분리

1단계(실시간 피치) 텍스트는 음을 확정한 뒤에도 계속 갱신된다 — 지금 마이크가 뭘 듣고 있는지 보여주는 순수 정보 표시라서 막을 이유가 없다. 반면 `MelodySession`에 기록하는 것(조성/화음이 바뀌는 원인)은 `hasCapturedNote`가 `true`가 되는 순간 멈춘다. 그리고 4단계 채점(`PitchScorer`)은 이 둘과 별개로 계속 돌아간다 — 채점은 "이미 고정된 목표음을 얼마나 잘 따라 부르는지"를 보는 것이라, 오히려 확정 이후에도 계속 마이크를 들어야 하기 때문이다. 이렇게 "언제 멈추고 언제 계속 돌아야 하는지"가 컴포넌트마다 다르다는 걸 하나의 콜백 안에서 조건문으로 구분해서 처리했다.

## 20. 멜로디 스텝별 채점 — "마지막 음만"이라는 제약 없애기

### 왜 마지막 음만 채점됐었나

`toggleScoring(interval:)`은 채점 목표를 고를 때 `melodySession.suggestedHarmony`를 봤는데, 이건 항상 `lastNote`(가장 최근에 잡은 음) 위에 쌓은 화음이다. 그래서 멜로디를 3개 불러도 채점 버튼을 누르면 항상 3번째(마지막) 스텝의 화음만 대상이 됐다 — 1번째·2번째 스텝은 채점할 방법이 아예 없었다.

### 해결: 스텝마다 자기 자신의 화음을 다시 계산

`startScoringMelodyStep(at:interval:)`은 `melodySession.suggestedHarmony`를 안 쓰고, 그 스텝의 `midiNote`로부터 주파수를 직접 구한 뒤 `ChordGenerator.generateHarmony(melodyFrequency:key:)`를 그 자리에서 다시 호출한다. `key`는 현재(가장 최신) 조성 판별 결과를 쓴다 — 스텝을 수정했을 때 전체 화음을 다시 계산하는 것(17절)과 같은 이유로, "화면에 보이는 모든 스텝이 같은 조성 가정을 공유한다"는 일관성을 유지한다.

이제 멜로디 목록의 각 줄에 "3도"/"5도" 버튼이 따로 붙어서, 몇 번째 음이든 원하는 스텝을 직접 골라 채점할 수 있다. 온음계 밖이라 화음이 없는 스텝(`harmonyNames == nil`)에는 애초에 이 버튼을 보여주지 않는다 — 존재하지 않는 화음을 채점할 수는 없으니까.

### "다시 시작"이 세션 기록은 건드리지 않는 이유

`resetSession()`은 현재 진행 중인 상태(멜로디 스텝, 조성, 채점 등)만 지운다. `PracticeAttempt`는 SwiftData에 저장된 별도 데이터라서, `@Query`로 화면에 표시되는 5단계(세션 기록)는 `resetSession()`이 손대는 어떤 `@State` 변수와도 무관하게 계속 남아있는다 — 원래부터 그렇게 분리돼 있었다.

## 21. 디지털 게인(AudioGain)과 "내 목소리로 전체 화음"

### 왜 `player.volume`으로는 소리를 못 키우나

`AVAudioPlayerNode`에는 `volume`이라는 프로퍼티가 있어서 얼핏 보면 이걸로 음량을 조절하면 될 것 같다. 하지만 이 값의 범위는 0~1이고, **1은 "원본 그대로", 0은 "무음"이라는 뜻이라 원본보다 더 크게 키우는 건 애초에 불가능하다.** 마이크로 녹음한 목소리는 보통 파형의 최대 진폭(피크)이 0.1~0.3 정도로 꽤 작게 들어오는데(사람마다, 마이크와의 거리마다 다름), `volume = 1.0`을 줘도 "작게 녹음된 걸 그대로" 재생할 뿐 커지지 않는다.

진짜로 체감 음량을 키우려면 **재생 직전에 샘플 값 자체를 스케일업**해야 한다 — 이게 `AudioGain.normalize(_:targetPeak:)`가 하는 일이다. 버퍼 전체에서 최댓값(피크)을 찾고, 그 피크가 `targetPeak`(기본 0.95 — 1.0에 너무 바짝 붙이면 디지털 클리핑 위험이 있어서 살짝 여유를 둠)가 되도록 전체 샘플에 같은 배율을 곱한다. 모든 샘플에 똑같은 배율을 곱하기 때문에 파형의 상대적인 모양(비율)은 그대로 유지되고, 크기만 커진다.

### 전체 화음을 "믹싱"하는 법

지금까지는 3도만, 또는 5도만 따로 들려줬는데, "화음 전체"를 들으려면 원음(뿌리음) + 3도로 옮긴 목소리 + 5도로 옮긴 목소리, 이 세 트랙을 **동시에** 들려줘야 한다. 오디오에서 여러 트랙을 "동시에 들리게" 만드는 가장 기본적인 방법은 같은 시간(인덱스)의 샘플 값을 그냥 더하는 것이다 — `mixAndNormalize`가 이 역할을 한다.

문제는 세 트랙의 길이가 정확히 같지 않을 수 있다는 것이다(`PitchShifter`가 시간축을 늘이고 리샘플링하는 과정에서 반올림 오차로 몇 샘플씩 차이가 날 수 있음). 그래서 셋 중 **가장 짧은 길이에 맞춰서** 그만큼만 더한다 — 어차피 그 이후는 어느 한쪽이 이미 끝난 구간이라 "셋이 같이 울리는" 순간이 아니다. 이렇게 더한 뒤에는 세 파형이 겹쳐진 만큼 진폭도 커져 있으므로(최악의 경우 3배까지), 마지막에 다시 `normalize`를 걸어서 클리핑 없이 targetPeak 안에 들어오게 정리한다.

### 왜 재생 직전(믹싱 후)에 한 번만 정규화하나

3도 트랙, 5도 트랙을 각각 먼저 정규화한 뒤에 더하면 안 되냐고 생각할 수 있는데, 그렇게 하면 각 트랙이 이미 최대치로 커진 상태에서 서로 더해지면서 거의 확실히 클리핑(값이 1.0을 넘어가서 소리가 찢어지는 현상)이 난다. 그래서 **원음 그대로의 상대적 크기로 먼저 섞고, 다 섞은 결과물 전체를 놓고 마지막에 한 번만 정규화**하는 순서가 맞다 — 이렇게 하면 세 목소리 사이의 자연스러운 상대적 크기(원래 부른 세기 차이)는 보존되면서, 결과물 전체의 음량만 최대한 키워진다.

`recordAndHarmonizeFullChordWithVoice()`는 이 순서를 그대로 따른다: 롤링 버퍼(`recentVoiceBuffer`)에서 원음을 가져오고, `PitchShifter.shift`로 3도/5도 버전을 각각 만든 뒤, `AudioGain.mixAndNormalize([recorded, third, fifth])`로 한 번에 섞고 키워서 재생한다. 무거운 연산(피치 시프트 두 번)이라 기존 3도/5도 단독 재생 함수와 마찬가지로 `Task { }`로 감싸 메인 스레드를 막지 않는다.

## 22. "음이 왔다갔다한다" — 롤링 버퍼에 섞인 이전 음/잡음을 잘라내기(VoiceSegmentTrimmer)

### 처음 의심했던 원인과 실측으로 기각한 이유

음성 재생이 불안정하다는 피드백을 받고 처음엔 WSOLA(21절 이전, `PitchShifter`)의 그레인 탐색이 매 그레인마다 "한 주기 앞/뒤"를 오락가락 고르는 것(=피치 주기보다 넓은 탐색 반경 때문에 생기는 전형적인 WSOLA 결함)이라고 의심했다. 그래서 `PitchShifter.shift`에 `expectedFrequency` 파라미터를 추가해서, 알고 있는 대략적인 기본 주파수로 탐색 반경을 반 주기 이하로 좁히도록 고쳤다.

그런데 이 가설이 맞는지 실제로 확인해보려고, `PitchShifter.swift`와 `YINPitchDetector.swift`만 따로 뽑아서(둘 다 Accelerate/Foundation만 쓰는 순수 코드라 앱 전체를 안 돌려도 됨) 커맨드라인에서 순음/유사 음성 합성 신호를 여러 잡음 수준으로 스윕하며 "탐색 반경을 좁히면 프레임별 검출 주파수의 흔들림(표준편차)이 줄어드는지" 직접 측정해봤다. 결과는 예상과 달리 애매했다 — 어떤 조건에서는 줄었지만 어떤 조건(특히 잡음이 클 때)에서는 오히려 늘기도 했고, 애초에 흔들림 크기 자체가 0.1~0.5Hz(1~3cent 이내) 수준으로 사람이 "왔다갔다한다"고 느낄 만한 크기가 아니었다. 즉 **이 경로로는 사용자가 보고한 증상을 설명하기 부족했다.** (파라미터 자체는 이론적으로 안전망 역할은 하므로 남겨뒀지만, "이게 원인이다"라고 확정하진 않았다.)

### 진짜 원인으로 더 유력한 것 — 롤링 버퍼는 "음 경계"를 모른다

`recentVoiceBuffer`(20절)는 버튼을 누른 시점과 무관하게 **최근 1.5초를 무조건** 담아두는 구조다. 그런데 이 버퍼는 순전히 오디오 샘플만 쌓을 뿐, "지금 이 부분이 어떤 음인지"는 전혀 모른다. 그래서 사용자가 방금 한 음을 부르기 직전에 다른 음을 부르고 있었거나, 숨을 들이쉬거나, 발음이 시작되는 잡음이 있었다면, 그 이전 소리가 버퍼 앞쪽에 그대로 섞여 있는 채로 버튼을 누를 수 있다. 이 버퍼 전체를 통째로 피치 시프트하면, **"한 음"이 아니라 "음이 바뀌는 구간"을 그대로 위로 옮기는 셈**이라, 재생했을 때 화음의 음정이 실제로 움직이는(왔다갔다하는) 소리가 난다 — 이건 착각이 아니라 원본 자체가 그런 내용을 담고 있기 때문이다. 특히 전체 화음(원음+3도+5도, 3트랙을 동시에 재생)에서 더 두드러지는 것도 이 설명과 맞는다 — 세 트랙이 전부 같은(불안정한) 원본에서 나왔으니, 그 불안정함이 세 목소리 모두에 똑같이 실려서 화음 전체가 흔들리는 것처럼 들린다.

### 해결: 최근의 "안정된 구간"만 잘라내기(VoiceSegmentTrimmer)

`VoiceSegmentTrimmer.trimToStableSegment(samples:sampleRate:targetFrequency:)`는 버퍼의 **맨 끝(가장 최근)부터 거꾸로** 훑으면서, 지금 화음의 기준이 된 음(`melodySession.lastNote?.frequency`)과 가까운(기본 ±60cent 이내) 동안만 계속 포함 범위를 앞으로 넓힌다. 처음으로 그 범위를 벗어나는 지점을 만나면 거기서 멈춘다 — 즉 "최근에 그 음을 부르고 있었던 연속 구간"만 남기고, 그 이전에 섞여 있던 다른 소리는 잘라낸다.

몇 가지 안전장치를 뒀다:
- 안정된 구간을 아예 못 찾으면(버퍼 전체가 목표음과 다르거나, 분석할 만큼 길지 않으면) **자르지 않고 원본을 그대로 반환**한다 — "화음이 아예 안 들리는" 것보다는 "예전처럼 다소 불안정하게라도 들리는" 쪽이 안전한 폴백이다.
- 잘라낸 결과가 너무 짧으면(0.2초 미만) 그것도 원본을 그대로 쓴다 — WSOLA 그레인(약 23ms)이 몇 개 안 남으면 오히려 더 부자연스러워질 수 있어서다.

`recordAndHarmonizeVoice`/`recordAndHarmonizeFullChordWithVoice` 둘 다 `PitchShifter.shift`를 호출하기 전에 이 트리머를 먼저 거친다 — 전체 화음에서는 원음(root) 트랙도 트리밍된 구간을 쓰도록 통일해서, 세 트랙이 정확히 같은 "안정된 한 음" 구간을 기준으로 만들어지게 했다.

### 원인을 못 찾았을 때 추측 대신 측정한 것

WSOLA 탐색 반경 가설이 맞는지 실제 실기기 청취 없이도(마이크로 직접 불러볼 순 없으니) 최소한 "이 가설이 수치로 보이는 흔들림을 줄이는가"는 확인할 수 있었다 — 합성 신호+실제 검출기(YIN)로 가설을 검증한 것. 결과가 기대와 다르게 나왔을 때 "그래도 이론적으로 그럴듯하니 맞다고 우기기"보다, 조건을 더 넓게 스윕해서 반증 사례가 나오는지 직접 찾아본 뒤 가설을 기각하고 다른 원인(버퍼에 섞인 이전 음)을 찾아나선 것이 이번 디버깅의 핵심이었다.

## 23. 멜로디 모드에서 "화음이 뒷부분만 들림" — 트리밍/버퍼 상한이 모드에 안 맞았던 문제

### 원인: 단음 모드 전용으로 설계한 걸 멜로디 모드에도 그대로 적용했다

22절의 `VoiceSegmentTrimmer`는 "롤링 버퍼 앞쪽에 섞인 예전 음을 잘라내고, 최근의 안정된 **한 음** 구간만 남긴다"는 목적으로 만들었다 — 단음 모드(한 음만 부르고 끝)를 염두에 둔 설계였다. 그런데 멜로디 모드는 애초에 여러 음을 이어 불러서(예: 도-미-솔) 그 전체를 화음으로 옮겨 듣고 싶어하는 모드다. 여기에 "마지막 음과 가까운 구간만 남기고 나머지는 잘라낸다"는 로직을 그대로 적용하면, **멜로디 전체 중 마지막 한 음만 남고 앞부분(먼저 부른 음들)은 전부 잘려나간다** — 사용자가 "화음이 뒷부분만 들려"라고 느낀 것과 정확히 일치한다. 거기에 더해 `recentVoiceBufferMaxDuration`(1.5초)도 단음 하나를 담기엔 충분하지만 멜로디 프레이즈 전체를 담기엔 짧아서, 애초에 버퍼 단계에서부터 앞부분이 잘려나가고 있었다.

### 해결: 모드별로 다르게 동작하게 분리

- **롤링 버퍼 상한**: `recentVoiceBufferMaxDuration`을 상수에서 `sessionMode`를 보는 계산 프로퍼티로 바꿔서, 단음 모드는 기존대로 1.5초, 멜로디 모드는 30초로 늘렸다. VAD를 통과한(=실제로 소리를 낸) 프레임만 버퍼에 쌓이므로, 30초는 "최대 한도"일 뿐 실제로는 부른 시간만큼만 채워진다.
- **트리밍 적용 여부**: `recordAndHarmonizeVoice`/`recordAndHarmonizeFullChordWithVoice`에서 `VoiceSegmentTrimmer`는 **단음 모드일 때만** 거치고, 멜로디 모드는 버퍼를 그대로(전체 다) 피치 시프트한다.

### 멜로디 모드에서 "화음"의 의미가 단음 모드와 다르다는 것

이 버그를 고치면서 다시 확인한 건, 멜로디 모드의 목소리 화음은 단음 모드와 성격이 다르다는 점이다 — `pitchRatio`는 여전히 "마지막 음 -> 그 음의 3도/5도" 하나의 배율로 계산되는데, 이 배율을 멜로디 전체(여러 음이 섞인 녹음)에 그대로 적용하면 모든 음이 **똑같은 반음 수만큼** 같이 올라간다. 이건 음마다 정확한 온음계 3도/5도를 다시 계산하는 것(마지막 음 기준 화음 생성, `MelodySession`)과는 다르고, "방금 부른 멜로디를 통째로 한 화음 간격만큼 위로 옮겨서 내 목소리로 들어보기"에 가깝다 — 정밀한 화성 이론보다는 "내 목소리로 하모니를 얹어서 들어보는" 체험에 가까운 단순화다. 지금 스코프에서는 이 정도로 충분하다고 보고 넘어갔다.

## 24. "음이 6개인데 화음은 5개만" — 롤링 버퍼가 음성 검출 성공 여부에 의존하고 있었던 근본 원인

### 진짜 원인: 버퍼가 "피치가 검출된 프레임"만 담고 있었다

23절까지 고친 뒤에도 사용자가 "음은 여섯 개인데 화음은 5개만 들리고, 자연스럽게 이어지는 느낌이 안 든다"고 피드백을 줬다. 코드를 다시 보니 `recentVoiceBuffer`에 샘플을 담는 코드가 애초부터 **`result`(VAD+YIN 피치 검출까지 성공한 경우에만 값이 있는 옵셔널)가 있을 때만** 실행되고 있었다:

```swift
guard let result else { ...; return }   // 검출 실패 시 여기서 함수가 끝나버림
...
recentVoiceBuffer.append(contentsOf: result.samples)  // 검출 성공한 프레임만 여기 도달
```

이게 두 가지 증상을 동시에 설명한다.
- **끊겨 들림(이어지는 느낌이 없음)**: 음과 음 사이에는 숨을 쉬거나 발음이 바뀌는 짧은 순간이 있는데, 그 프레임은 VAD가 무음으로 판정하거나(에너지 낮음) YIN이 명확한 피치를 못 찾아서 `result`가 `nil`이 되고, 그 프레임의 원본 오디오는 통째로 버려졌다. 그 결과 버퍼에는 "음 1의 오디오" 바로 뒤에 "음 2의 오디오"가 **시간축 이음매 없이(마치 원래 그렇게 붙어있던 것처럼)** 잘려 붙어 있었다 — 실제로 부른 자연스러운 타이밍/숨쉬는 틈이 전부 사라진 것이다. 이걸 WSOLA로 피치 시프트하면 이 인위적인 이음매 자체가 부자연스럽게 들린다.
- **음 하나가 통째로 빠짐(6개 중 5개만 들림)**: 어떤 음이 짧거나, 약하게 불렀거나, 시작/끝에 숨이 섞였다면 그 음의 모든 프레임이 우연히 VAD/YIN에서 계속 실패할 수 있다 — 그러면 그 음은 `recentVoiceBuffer`에 단 한 샘플도 안 들어간다. 화면에 표시되는 `melodySteps`(6개)는 `result`가 있을 때만 갱신되는 게 아니라 조금 다른 경로로 확정되므로 6개로 보이지만, 정작 오디오 버퍼 쪽에서는 그 음이 완전히 빠진 것이다.

### 해결: "판단"과 "녹음"을 분리한다

`AudioCapture`의 콜백은 원래 "피치 검출 성공 여부"와 "그 프레임의 원본 오디오"를 한 덩어리(`DetectionResult?`)로 묶어서 넘기고 있었다. 그런데 이 둘은 용도가 다르다 — 조성 판별/화음 생성/채점 같은 로직은 "이 프레임에서 확실한 피치가 검출됐는가"만 신경 쓰면 되지만(그래서 `nil`을 건너뛰는 게 맞다), "내 목소리를 그대로 녹음해서 화음 만들기"는 검출 성공 여부와 무관하게 **그 순간 마이크가 실제로 잡은 파형**이 필요하다.

그래서 `AudioCapture.ResultHandler`의 시그니처를 `(DetectionResult?) -> Void`에서 `(DetectionResult?, rawSamples: [Float], rawSampleRate: Double) -> Void`로 바꿨다 — `result`는 기존처럼 피치 판단 로직에 쓰고, `rawSamples`는 검출 성공/실패와 무관하게 **매 프레임 항상** 넘어온다. `recentVoiceBuffer`는 이제 `rawSamples`를 쓰기 때문에, 음 사이의 숨소리·짧은 무음도 원래 타이밍 그대로 버퍼에 남고, 아무리 짧거나 조용한 음이라도 마이크가 소리를 잡은 이상 버퍼에서 빠지지 않는다.

### 이 변경이 22절(VoiceSegmentTrimmer)에 미친 영향

`VoiceSegmentTrimmer`(22절)는 원래 "버퍼 끝부분이 항상 검출 성공한 프레임"이라는 전제로, 끝에서부터 목표음과 다른 게 나오면 바로 멈추도록 짜여 있었다. 그런데 이제 버퍼 끝에 노래를 마친 뒤의 **진짜 무음 꼬리**가 섞여 있을 수 있다(예전엔 그 무음 프레임 자체가 버퍼에 안 들어갔지만, 지금은 들어간다). 이 무음 꼬리 때문에 트리머가 곧바로 멈춰서 "안정 구간을 못 찾음" 폴백으로 빠지면 안 되므로, `VoiceActivityDetector.isVoiceActive`로 "아직 진짜 소리에 도달하기 전의 무음"과 "한 번 소리 구간에 들어선 뒤 다시 나온 무음(=진짜 음 경계)"을 구분해서, 전자는 건너뛰고 후자에서만 멈추도록 보완했다.

## 25. "화음 만드는데 왜 이렇게 오래 걸리냐" — 디버그 빌드 최적화 + vDSP 벡터화

### 원인 두 가지가 겹쳤다

1. **Xcode Debug 빌드는 기본적으로 최적화가 꺼져 있다**(`SWIFT_OPTIMIZATION_LEVEL = -Onone`). 21절에서 "제스처 게이트 타임아웃" 버그를 고칠 때 이미 한 번 마주쳤던 문제와 같은 원인인데, 그때는 "메인 스레드를 막지 않기"(`Task {}`)로 우회했을 뿐, 연산 자체가 느린 근본 원인은 그대로 남아 있었다.
2. **23절에서 멜로디 모드의 롤링 버퍼 상한을 1.5초 -> 30초로 늘렸다.** WSOLA(`PitchShifter.timeStretch`)의 연산량은 입력 길이에 비례해서 늘어나는데(그레인 개수 자체가 길이에 비례), 버퍼가 길어진 만큼 연산량도 그대로 늘었다. 게다가 "전체 화음"은 같은 버퍼를 3도/5도 두 번 시프트하므로 부담이 두 배다.

### 해결 1 — Debug 빌드에서도 최적화 컴파일 켜기

`project.yml`의 앱 타겟에 `settings.configs.Debug.SWIFT_OPTIMIZATION_LEVEL: "-O"`를 추가했다. Debug 설정 이름은 그대로 유지하면서(어서션 등은 남아있음) 컴파일 최적화만 Release 수준으로 올리는 방식이다 — 실기기 성능 확인이 이 프로젝트의 핵심 작업 방식이라 디버깅 편의(정확한 줄 단위 스테핑)보다 실제 체감 속도가 더 중요하다고 판단했다. (수정 후 시뮬레이터 유닛테스트 실행 시간이 약 1.5초 -> 0.06초로 줄어든 것으로 최적화가 실제로 적용됐음을 확인했다.)

### 해결 2 — WSOLA의 가장 무거운 루프를 Accelerate(vDSP)로 벡터화

`bestMatchingOffset`은 탐색 반경 안의 모든 후보 위치마다 길이 `compareLength`짜리 내적(dot product)을 계산한다 — 이게 WSOLA 전체 연산량의 대부분을 차지한다. 원래는 순수 Swift `for` 루프(`score += samples[a+i] * samples[b+i]`)로 짜여 있었는데, 이걸 `vDSP_dotpr`(Accelerate 프레임워크의 벡터화된 내적 함수)로 바꿨다. `vDSP_dotpr`는 이미 최적화된 바이너리로 컴파일돼 있어서, **호출하는 쪽 코드의 컴파일 최적화 수준과 무관하게** 하드웨어 SIMD(여러 개의 곱셈/덧셈을 한 명령으로 처리) 명령을 활용한다 — 그래서 위 1번 최적화와 별개로도 효과가 있고, 둘을 합치면 더 크게 빨라진다. `YINPitchDetector`가 이미 자기상관 계산에 Accelerate를 쓰고 있었는데(신호처리 코드에서 내적/자기상관처럼 규칙적인 반복 연산은 Accelerate로 벡터화하는 게 관례라는 걸 다시 확인한 셈), 같은 패턴을 `PitchShifter`에도 적용한 것이다.

## 26. "화음이 다 안 들려" 진짜 원인 — 목소리 화음 재생만 콜앤리스폰스 규칙에서 빠져 있었다

### 이 프로젝트의 오래된 규칙 하나를 목소리 화음 재생만 깜빡했다

Phase 3 초반부터 이 프로젝트는 "재생 중엔 마이크를 완전히 무시한다"는 규칙을 지켜왔다(`isPlaybackBusy`) — 스피커로 낸 소리가 마이크로 되먹임돼서 "새로 부른 음"으로 잘못 인식되는 피드백 루프를 막기 위해서다. `TonePlayer`(목표음/시작음), 멜로디 라인 재생은 전부 이 규칙을 따르는데, **"내 목소리로 화음 만들기"(`VoiceClipPlayer`)만 여기서 빠져 있었다.** `isPlaybackBusy`가 `isPlayingTone`, `isPlayingStartingNote`, `playingMelodyLineInterval`만 보고 목소리 화음 재생 상태는 아예 추적하지 않고 있었던 것이다.

그 결과: 목소리 화음을 재생하는 몇 초 동안에도 마이크는 계속 켜진 채로 남아있었고(멜로디 모드는 채점 중이 아니면 캡처 가드가 없으므로 `shouldEvaluateCapture`가 항상 참), 스피커로 나온 화음(3도/5도 목소리)을 마이크가 다시 듣고 **엉뚱한 pitch class를 가진 "새 멜로디 음"으로 착각**해서 `melodySession`에 계속 추가했다. 이건 조성 판별용 히스토그램과 `lastNote`/`suggestedHarmony`를 실시간으로 오염시킨다 — 그래서 재생을 할수록(특히 멜로디가 길어서 "전체 화음"을 오래 재생할수록) 다음 계산에 쓰이는 상태가 점점 더 부정확해지고, 사용자가 "특히 마지막 전체 화음할 때 음이 빠진다"고 느낀 것과 맞아떨어진다 — 누적 오염이 뒤로 갈수록 커지기 때문이다.

### 해결: 재생 완료 시점을 정확히 알고, isPlaybackBusy에 포함시키기

`VoiceClipPlayer.play(samples:sampleRate:)`는 원래 `player.scheduleBuffer(buffer, completionHandler: nil)`로 재생을 예약만 하고 "언제 끝나는지"는 아무도 몰랐다. `completionCallbackType: .dataPlayedBack`을 지정한 `onFinished` 콜백을 추가해서, **버퍼가 큐에 들어간 시점이 아니라 실제로 스피커까지 소리가 다 나간 시점**에 정확히 알림을 받도록 고쳤다(콜백은 오디오 스레드에서 오므로 메인 큐로 넘겨서 호출).

`ContentView`에는 `isPlayingVoiceClip` 상태를 추가해서 `isPlaybackBusy`에 포함시켰다 — 재생 시작 직전에 `true`, `onFinished`에서 `false`로. 이제 목소리 화음을 재생하는 동안에도 다른 재생과 똑같이 마이크가 완전히 무시되고, 재생이 실제로 끝난 뒤에야 다시 켜진다.

## 27. 출력을 더 깔끔하게 — 오버랩 늘리기 + 클릭음 제거

"기능은 잘 되는데 소리를 더 다듬어달라"는 요청에 맞춰, WSOLA 결과물이 지저분하게 들리는 대표적인 두 가지 원인을 손봤다.

### 오버랩을 75% -> 87.5%로

WSOLA는 그레인을 겹쳐서(overlap-add) 이어붙이는데, 겹치는 비율이 낮을수록 그레인 사이 경계가 도드라져서 "지지직"거리거나 로봇 음성처럼 들리기 쉽다. 원래는 `hopDivisor = 4`(75% 겹침)였는데 `8`(87.5% 겹침)로 올렸다.

보통은 오버랩을 늘리면 그레인 개수가 늘어난 만큼 연산량도 늘어날 거라 생각하기 쉽지만, 이 코드에서는 그렇지 않다 — 25절 이후로 그레인마다 상관관계를 탐색하는 반경(`searchRadius`)이 `hop` 자체가 아니라 **피치 주기**에 맞춰 제한돼 있어서, `hop`을 줄여도 탐색 반경은 그대로다. 탐색 비용(그레인당 지배적인 연산)이 `(그레인 개수) x (탐색 반경 x 비교 길이)`로 결정되는데, 그레인 개수는 `hop`에 반비례(`hop` 절반 -> 그레인 2배)하고 비교 길이(`compareLength = hop`)는 `hop`에 비례(`hop` 절반 -> 비교 길이 절반)해서, 이 둘이 서로 상쇄돼 총 탐색 비용은 `hop`과 거의 무관하게 유지된다. 늘어나는 건 그레인마다 한 번씩 하는 창(window) 적용 비용(`O(grainSize)`, 탐색 비용에 비하면 훨씬 작다) 뿐이라, 사실상 "거의 공짜"로 오버랩을 늘릴 수 있었다 — vDSP 벡터화(25절)로 확보한 여유를 소리 품질에 재투자한 셈이다.

### 재생 시작/끝의 클릭음 제거 — 페이드 인/아웃

롤링 버퍼에서 잘라낸 구간(`VoiceSegmentTrimmer`가 트리밍한 결과, 또는 멜로디 모드의 롤링 버퍼 전체)은 원본 노래의 임의의 지점에서 시작하고 끝난다 — 파형이 정확히 0인 지점에서 잘린다는 보장이 없다. 디지털 오디오에서 파형 값이 0이 아닌 채로 갑자기 시작되거나 끊기면, 그 순간의 급격한 진폭 변화(불연속) 자체가 스피커에서 "뚝"하는 클릭음으로 들린다.

`AudioGain.applyFadeInOut(_:fadeSampleCount:)`을 추가해서, 버퍼의 맨 앞과 맨 뒤를 짧게(15ms) 선형으로 0까지 줄이도록(반대로 앞은 0에서 시작해서 올라오도록) 했다. 15ms는 사람이 "소리가 점점 커진다/작아진다"고 느끼기엔 너무 짧아서 음량 변화로는 거의 인지되지 않으면서도, 시작/끝 지점을 확실히 0으로 만들어 클릭음을 없앤다. 목소리 화음 재생(단독 3도/5도, 전체 화음) 둘 다 `AudioGain.normalize`/`mixAndNormalize`로 음량을 정리한 **다음** 마지막 단계로 이 페이드를 적용한다 — 음량 정규화는 피크 기준으로 계산되므로 순서를 바꿔도 상관없지만, "재생 직전 마지막 손질"이라는 의미상 맨 끝에 두는 게 자연스럽다.

## 28. UI/UX 리디자인 착수 — 디자인 시스템 기반(Theme.swift)

### 왜 지금 디자인을 손보나

Phase 1~3와 "내 목소리로 화음 만들기"까지 핵심 기능이 전부 실기기에서 검증됐다. 지금까지는 CLAUDE.md 원칙대로 "기능 먼저, 디자인은 나중"으로 진행해서, 화면은 여전히 1~5번 숫자를 붙인 섹션이 쌓인 디버그용 스크롤 화면이었다(`ContentView.swift`의 `flowSection` 헬퍼). 이제 기능이 안정됐으니 UI/UX를 실제 제품 수준으로 다듬는 단계로 넘어간다.

### 화면 구조를 "번호 파이프라인" 대신 "카드 목록"으로 바꾸는 이유

지금은 측정→조성→화음→채점 순서가 자연스럽지만, 사용자가 "나중에 메인 기능은 채점이 아닐 수도 있다"(예: "내 목소리로 화음 만들기"가 더 중요해질 수 있음)고 명확히 밝혔다. 그래서 화면을 1~5 고정 번호가 아니라, 각 기능을 독립된 카드(View)로 분리하는 방향으로 설계했다 — 나중에 어떤 기능이 더 중요해지든 카드 순서만 바꾸면 되게 하기 위해서다.

### 디자인 시스템에 새 컬러 대신 시스템 시맨틱 컬러를 우선한 이유

iOS Human Interface Guidelines는 "하나의 틴트 컬러가 인터랙션 요소를 이끈다"와 "시맨틱 시스템 컬러(라벨, 배경 등)를 쓰면 다크모드/고대비에 자동으로 대응하지만, 커스텀 hex는 그렇지 않다"를 명시한다. 그래서:
- 버튼/피커 등 인터랙션 요소의 틴트는 `Theme.tint` **하나만** 쓴다. "내 목소리로 화음" 계열을 시각적으로 구분하고 싶어서 두 번째 브랜드색(`Theme.voiceAccent`)을 만들었지만, 이건 버튼 틴트가 아니라 아이콘/라벨 같은 장식에만 쓴다 — 인터랙션 요소에 색이 두 개 이상 경쟁하면 "뭐가 눌리는 버튼인지" 헷갈리기 쉽다.
- 카드 배경, 화면 배경 같은 나머지는 새로 정의하지 않고 `Color(uiColor: .secondarySystemGroupedBackground)`처럼 애플이 이미 라이트/다크 양쪽에 맞춰둔 시맨틱 컬러를 그대로 쓴다.
- 커스텀 색(브랜드 틴트, 보조 강조색)은 `Color(light:dark:)`라는 작은 확장(내부적으로 `UIColor { traits in ... }` — 트레이트 컬렉션의 `userInterfaceStyle`을 보고 라이트/다크 각각 다른 색을 반환)으로 명시적으로 두 값을 다 정의해서, 시스템이 모르는 색이라도 다크모드 전환에 제대로 반응하게 했다.

### 검증 방법 — 시뮬레이터 스크린샷으로 라이트/다크 직접 비교

`xcrun simctl io <UDID> screenshot`으로 시뮬레이터 화면을 캡처하고, `xcrun simctl ui <UDID> appearance dark`로 다크모드를 강제 전환해서 같은 화면을 다시 캡처하는 방식으로 라이트/다크 양쪽에서 새 틴트가 제대로 보이는지 눈으로 직접 확인했다. 지금까지는 실기기 설치 후 사람이 눈으로 보는 방식에 의존했는데, UI 변경은 시뮬레이터 스크린샷만으로도 상당 부분 즉시 검증할 수 있다는 걸 확인했다(실기기는 여전히 최종 확인 단계에서 필요 — 특히 마이크 권한 등 시뮬레이터로 재현 안 되는 부분).

## 29. 탭 2개 + 카드 분리 — 화면을 실제로 여러 조각으로 나누기

### 화면 파일을 쪼갠 방식

`ContentView.swift` 하나(955줄)에 있던 걸 역할별로 나눴다:
- `HarmonyUpApp.swift`가 이제 `ContentView()` 대신 `RootTabView()`를 띄운다.
- `RootTabView.swift` — `TabView`로 "연습"/"기록" 탭 2개를 구성한다. iOS HIG는 "탭바는 액션이 아니라 섹션에만 쓴다"고 명시하는데, 연습(캡처~채점)과 기록(과거 열람)은 서로 다른 사용 맥락의 진짜 섹션이라 이 조건에 맞는다.
- `ContentView.swift`는 `PracticeView.swift`로 이름을 바꿨다(역할이 "유일한 화면"에서 "연습 탭 화면"으로 좁혀졌으므로). **State/로직은 전부 그대로 옮겼고, `body`만 다시 짰다** — 리스크를 낮추기 위해 한 번에 로직까지 재배치하지 않았다.
- `HistoryView.swift` — 기존 "5. 세션 기록" 섹션을 통째로 옮겨서 독립된 화면으로 만들었다. `@Query`도 여기로 옮겨서, 연습 화면은 더 이상 기록 데이터를 몰라도 된다.
- `MelodyStepRow.swift` — 멜로디 스텝 한 줄(수정 메뉴 + 화음 표시 + 3도/5도 버튼)을 별도 View로 뽑았다. 재사용하려는 목적보다는, `PracticeView`의 `body`가 한 파일 안에서 너무 깊게 중첩되는 걸 막기 위해서다. 이 스텝이 참조하던 `MelodyStep` 구조체(`private`였던 걸 이 파일로 옮기며 `private` 제거)도 같이 옮겼다 — 모델을 그 모델을 가장 많이 쓰는 뷰 옆에 두는 편이 찾기 쉽다.

### 점진적 공개(progressive disclosure)를 실제로 적용

이전엔 5개 섹션이 처음부터 전부 보이고, 데이터가 없으면 "아직 판별되지 않음" 같은 빈 상태 텍스트만 보여줬다. 지금은 SwiftUI의 `if` 조건으로 카드 자체를 렌더링하지 않는다 — `hasCapturedNote`(첫 음이 잡혔는지), `melodySession.suggestedHarmony != nil`(화음이 나왔는지) 같은, 이미 존재하던 상태 변수를 그대로 재사용해서 "조성과 화음", "내 목소리로 화음", "따라 부르기 채점" 카드의 등장 여부를 결정한다. 새로운 상태를 추가하지 않고 기존 조건을 뷰 레이어의 가시성 조건으로 승격시킨 것뿐이라, 로직이 하나도 안 바뀌었는데도 "처음 켰을 때 화면이 훨씬 단순해 보이는" 효과를 얻었다.

### iOS 시뮬레이터에서 실제로 탭을 눌러 확인하는 법

`xcrun simctl`에는 화면을 탭하는 명령이 따로 없다(스크린샷/실행/설치 정도만 지원). 대신 macOS Accessibility API를 통해 `osascript`(AppleScript)로 Simulator 앱 창의 특정 좌표를 클릭할 수 있다 — 시뮬레이터 창의 위치/크기(`System Events`로 조회)와 스크린샷의 실제 픽셀 크기 비율을 이용해서, 화면 속 탭바 버튼의 좌표를 창 좌표로 환산해 클릭했다. 실제로 "기록" 탭으로 전환되는 것까지 스크린샷으로 확인했다 — 코드만 읽고 "아마 될 것"이라고 넘기지 않고, 실제 탭 전환 동작을 시뮬레이터에서 직접 재현해본 것.

## 30. 폰트를 Pretendard로 통일하기 — iOS에 커스텀 폰트를 넣는 법

### 왜 폰트 파일이 필요한가

iOS 기본 시스템 폰트는 San Francisco(SF)인데, 한글은 SF가 아니라 애플이 자동으로 매칭해주는 "SD 산돌고딕Neo"로 렌더링된다. "Pretendard로 통일해달라"는 건 이 기본 한글 폰트를 다른 폰트로 바꿔달라는 것이다 — iOS에서 시스템 폰트가 아닌 폰트를 쓰려면, **폰트 파일(.otf/.ttf) 자체를 앱 번들 안에 넣고 등록**해야 한다. 이미 컴퓨터에 설치된 폰트를 쓰는 macOS 개발과 달리, iOS 앱은 "이 폰트가 기기에 있을 것"이라고 가정할 수 없다.

### Pretendard를 받아온 방법

[Pretendard](https://github.com/orioncactus/pretendard)는 SIL Open Font License(OFL) 1.1로 배포되는 오픈소스 폰트라 앱에 자유롭게 포함할 수 있다. GitHub 릴리즈에는 굵기별 정적 파일과 가변 폰트(variable font)가 다 들어있는 47MB짜리 zip이 있는데, 여기서 실제로 쓸 4개 굵기(Regular/Medium/SemiBold/Bold)의 `.otf`만 뽑아서 `HarmonyUp/Sources/Resources/Fonts/`에 넣었다(전체 6MB) — 가변 폰트는 SwiftUI에서 굵기 축(weight axis)을 다루려면 별도 처리가 필요해서, 지금 필요한 굵기만 정적 파일로 받는 게 더 간단했다. 라이선스 조건(OFL은 재배포 시 라이선스 텍스트 동봉을 요구)에 맞춰 `LICENSE.txt`도 같이 넣었다.

### 폰트를 실제로 코드에서 쓰기까지 — 세 가지가 다 맞아야 한다

1. **폰트 파일이 앱 번들에 들어있어야 한다** — XcodeGen은 `sources:` 경로 아래 있는 파일을 확장자로 분류해서, 코드가 아닌 파일(`.otf` 등)은 자동으로 "Copy Bundle Resources" 빌드 단계에 넣어준다. 별도 설정 없이 폴더에 넣기만 하면 됐다(`.pbxproj`에 `Pretendard-Regular.otf in Resources` 같은 항목이 생기는 걸로 확인).
2. **`Info.plist`에 `UIAppFonts` 키로 파일명을 등록해야 한다** — 이게 없으면 폰트 파일이 번들 안에 있어도 iOS가 시스템에 "설치"하지 않아서 `Font.custom(...)`이 조용히 시스템 폰트로 폴백한다(에러가 나지 않아서 원인 찾기가 까다롭다). 여기서 삽질을 한 번 했다 — `Info.plist`를 직접 열어서 키를 추가했는데, `xcodegen generate`를 다시 돌리자 그 변경이 통째로 사라졌다. 이유는 `project.yml`의 `info.properties`가 매번 `Info.plist`를 **재생성**하기 때문 — 그 파일은 손으로 고치는 파일이 아니라 XcodeGen이 매번 새로 쓰는 산출물이었다. 그래서 `UIAppFonts`도 `project.yml`의 `info.properties` 쪽에 넣도록 고쳤다. (`project.yml`에서 관리하는 값과 `Info.plist` 파일을 둘 다 손으로 만지면 이렇게 예상 못 한 순간에 덮어써질 수 있다는 걸 다시 확인한 사례.)
3. **정확한 PostScript 이름으로 불러와야 한다** — `Font.custom("이름", size:)`의 "이름"은 파일명이 아니라 폰트 내부에 저장된 PostScript 이름이다. 이 이름은 폰트 파일의 `name` 테이블(폰트 포맷 안에 있는 메타데이터 영역)에 들어있는데, `fc-scan`이나 `fontTools` 같은 도구가 없어도 그 테이블은 공개된 이진 포맷이라 직접 파싱할 수 있다 — 파이썬 표준 라이브러리(`struct`)만으로 짧은 스크립트를 짜서 4개 파일의 PostScript 이름(`Pretendard-Regular`, `-Medium`, `-SemiBold`, `-Bold`)을 직접 확인했다.

### Dynamic Type을 유지하면서 커스텀 폰트 쓰기

iOS HIG는 "하드코딩된 포인트 크기 대신 시스템 텍스트 스타일을 써서, 사용자가 설정에서 글자 크기를 키우면 텍스트도 같이 커지게 하라"고 명시한다(Dynamic Type). 커스텀 폰트를 쓰면 이 자동 크기 조절이 사라질 것 같지만, SwiftUI의 `Font.custom(_:size:relativeTo:)`는 `relativeTo:`에 넘긴 시스템 텍스트 스타일(`.body`, `.title3` 등)을 기준으로 커스텀 폰트도 같이 스케일되게 해준다. `Theme.Typography`에 이 함수를 감싼 이름 있는 상수(`title3Bold`, `headline`, `body` 등)를 만들어서, 코드에서는 `.font(.title3.bold())` 대신 `.font(Theme.Typography.title3Bold)`처럼 쓰게 했다 — 겉보기엔 시스템 폰트를 쓰던 것과 똑같은 자리에 그대로 대입하는 것뿐이지만, 실제로는 Pretendard로 렌더링되면서 Dynamic Type도 그대로 작동한다.

### 예외 — 실시간 숫자는 그대로 시스템 모노스페이스

Hz/cent/시간처럼 자주 갱신되는 숫자 표시(`.font(.system(..., design: .monospaced))`로 쓰던 곳)는 Pretendard로 바꾸지 않고 그대로 뒀다. 모노스페이스를 쓴 원래 이유가 "자릿수가 바뀔 때 폭이 흔들리지 않게" 하기 위해서였는데(이전 절 참고), Pretendard는 가변폭 폰트라 이 속성이 없다 — 폰트를 통일하는 김에 이 예외까지 없애버리면 오히려 이전에 고쳤던 문제가 되살아난다. "폰트 통일"이라는 요청을 글자 그대로 전부 적용하는 대신, 그 요청의 목적(가독성/일관된 인상)과 배치되지 않는 선에서 기존에 의도적으로 넣어둔 예외는 남겨뒀다.

## 31. 마이크 권한 거부 상태 전용 UI + 시뮬레이터로 권한 상태 강제 재현하기

### 왜 필요했나

29절 계획에서 "캡처 카드가 마이크 권한 거부를 제대로 안내하지 못한다"는 문제를 남겨뒀었다 — 이전엔 `audioCapture.start()`가 실패하면 그냥 `statusText`에 에러 메시지 한 줄이 섞여 나올 뿐이라, 사용자가 "버튼이 안 눌리네?"라고 오해하기 쉬웠다.

### 권한 확인 -> 요청 -> 안내, 세 단계로 분리

`beginCapturingIfNeeded()`가 실제로 마이크를 켜기 전에 `AVAudioApplication.shared.recordPermission`(iOS 17+에서 마이크 권한을 다루는 API — 예전엔 `AVAudioSession`에 있었는데 iOS 17부터 이 쪽으로 옮겨졌다)을 먼저 확인한다:
- **`.granted`**: 바로 캡처 시작.
- **`.denied`**: 캡처를 시도하지 않고 `micPermissionDenied = true`만 켠다 — 이 상태를 화면이 감지해서 "마이크 권한이 꺼져 있어요" 전용 UI(마이크-슬래시 아이콘 + 설명 + "설정 열기" 버튼)를 보여준다. "설정 열기"는 `UIApplication.openSettingsURLString`으로 iOS 설정 앱의 이 앱 권한 화면으로 바로 이동시킨다.
- **`.undetermined`**(아직 한 번도 물어본 적 없음): `AVAudioApplication.requestRecordPermission { granted in ... }`으로 시스템 권한 팝업을 띄우고, 결과에 따라 캡처를 시작하거나 거부 UI를 보여준다.

또한 화면이 나타날 때(`.onAppear`)도 한 번 상태를 확인해서, 사용자가 "측정 시작"을 누르기도 전에 이미 이전에 거부한 상태라면 미리 알려준다 — 버튼을 눌러야만 알 수 있는 것보다 먼저 보여주는 게 더 친절하다.

### 시뮬레이터에서 "거부된 상태"를 실제로 재현해서 확인하는 법

권한 관련 UI는 실제로 그 상태가 아니면 눈으로 볼 수가 없어서, 코드 리뷰만으로는 "아마 맞을 것"이라고 넘어가기 쉬운 부분이다. `xcrun simctl privacy <시뮬레이터 UDID> revoke microphone <번들ID>`로 시뮬레이터에서 이 앱의 마이크 권한을 강제로 거부 상태로 만들 수 있다(반대는 `grant`) — 실제로 권한을 거부해본 뒤 앱을 실행해서 스크린샷으로 "마이크 권한이 꺼져 있어요" 화면이 정확히 뜨는 걸 확인했다. 확인 후엔 다시 `grant`로 되돌려서 다음 테스트에 영향이 없게 정리했다.

## 32. Dynamic Type 최대 크기로 실제로 켜보고 깨지는 곳 고치기

### 왜 "될 것 같다"로 넘기면 안 되는가

HIG는 하드코딩된 포인트 크기 대신 시스템 텍스트 스타일을 쓰라고 하는데(30절), 그렇게 만들어도 "글자가 커지면 레이아웃이 어떻게 반응하는지"는 또 다른 문제다. 특히 `HStack`으로 나란히 배치한 버튼/피커는, 평소 글자 크기에선 잘 맞아 보여도 사용자가 설정에서 글자를 아주 크게 키우면(접근성 확장 크기) 가로 폭이 부족해져서 내용물이 찌그러지거나 겹칠 수 있다. 이건 코드만 읽어서는 예측하기 어렵고, 실제로 그 크기로 켜서 봐야 보인다.

### 시뮬레이터에서 강제로 가장 큰 글자 크기로 켜보기

`xcrun simctl ui <UDID> content_size accessibility-extra-extra-extra-large`로 시뮬레이터의 글자 크기를 iOS가 지원하는 가장 큰 단계로 강제 설정할 수 있다. 이 상태로 앱을 실행해서 스크린샷을 찍어보니, "시작음 듣기" 버튼이 있는 `HStack`(피커 + 버튼)이 가로 폭에 다 안 들어가서 버튼 텍스트가 알약 모양 밖으로 삐져나오고 뒤에 있던 다른 텍스트와 겹치는 게 실제로 보였다 — 평소 크기에서 리뷰할 땐 전혀 안 보이던 문제였다.

### 해결: `ViewThatFits`로 "안 들어가면 세로로" 자동 전환

`ViewThatFits`는 여러 후보 레이아웃을 순서대로 줘서, 그 중 실제로 주어진 공간에 들어가는 첫 번째 것을 골라 쓰게 해주는 SwiftUI 컨테이너다. 가로 `HStack` 버전을 먼저 주고, 안 들어가면 세로 `VStack` 버전으로 자동으로 넘어가게 했다 — 이렇게 하면 평소 글자 크기에선 기존처럼 가로로 나란히 보이고, 글자가 커져서 가로에 못 들어가는 상황에서만 세로로 쌓인다(찌그러지거나 겹치지 않고, 그냥 줄이 늘어날 뿐). "시작음 듣기" 컨트롤(2곳에서 재사용), "전체 3도/5도 듣기" 버튼 2개, "내 목소리로 3도/5도/전체 화음" 버튼 3개, 이렇게 버튼이 여러 개 나란히 있던 자리 전부에 같은 패턴을 적용했다. `.buttonStyle(...)`/`.disabled(...)` 같은 수정자는 `ViewThatFits` 바깥에 한 번만 걸어두면 안의 두 레이아웃(가로/세로) 어느 쪽이 선택되든 똑같이 적용된다 — SwiftUI의 수정자가 값을 환경(environment)으로 전달하는 방식이라 가능한 것이다.

## 33. 녹음 파형 시각화(WaveformView)

### 왜 필요했나

사용자가 다른 음성 녹음 앱들(레퍼런스 이미지)을 보여주며 "녹음할 때 파형이 UI로 보이게" 요청했다. 지금까지 "측정 중"이라는 상태는 텍스트(`statusText`)로만 표현됐는데, 실제로 마이크가 소리를 듣고 있다는 걸 훨씬 직관적으로 보여주는 방법이 파형이다.

### 원본 샘플을 그대로 그릴 수 없는 이유와 다운샘플링

마이크 원본은 초당 44,100개 샘플이 들어온다 — 화면에 이걸 그대로 막대로 그리면 막대가 픽셀보다 많아진다. `WaveformView`는 보여줄 막대 개수(기본 40개)만큼 구간을 나누고, 각 구간에서 **절대값 기준 최댓값(피크)**을 뽑아 그 구간을 대표하는 높이로 쓴다 — 평균이 아니라 피크를 쓰는 이유는, 짧고 큰 소리(예: 자음 시작)가 평균에 묻혀 사라지지 않게 하기 위해서다.

### 정규화 — "지금 보이는 구간 안에서" 가장 큰 소리를 기준으로 다시 스케일

마이크로 녹음한 원본은 피크가 보통 0.1~0.3 정도로 낮게 들어온다(이미 AudioGain에서 다룬 것과 같은 특성). 이 값을 그대로 막대 높이 비율로 쓰면 파형이 화면 아래쪽에서만 작게 움직여서 "녹음되고 있다"는 느낌이 잘 안 산다. 그래서 다운샘플링한 구간별 피크들 중 **지금 화면에 보이는 것들 중 가장 큰 값**을 찾아서, 그 값을 1.0으로 놓고 나머지를 그 비율로 다시 스케일한다 — 매 프레임 이 최댓값이 갱신되므로, 사용자가 크게 부르면 파형이 화면을 꽉 채우고 작게 부르면 상대적으로 아담하게 움직인다(항상 "지금 낼 수 있는 가장 큰 소리" 기준으로 반응하는 것).

### 파형을 어디에 붙였나 — 캡처 카드 하나로 통합

레퍼런스 이미지들은 "녹음"이 앱의 메인 화면 전체를 차지하는 전용 화면이었지만, 이 앱은 실시간 피치 측정(계속 켜져 있는 마이크)과 "내 목소리로 화음" 녹음(같은 마이크 입력을 재사용하는 롤링 버퍼)이 하나의 "측정 시작/중지" 토글을 공유하는 구조다. 그래서 파형을 별도 화면이나 카드로 새로 만들지 않고, 이미 있던 "실시간 피치" 카드 안에 `isCapturing`일 때만 나타나는 블록으로 넣었다 — 두 기능(피치 측정 + 목소리 녹음)이 같은 마이크 캡처를 공유한다는 사실을 화면 구조에도 그대로 반영한 것.

### 정보 밀도 정리

"정보가 몰려있다"는 피드백에 맞춰, 캡처 카드 안을 세 그룹(측정 버튼 -> 파형+판독값 -> 시작음 컨트롤)으로 나누고 그룹 사이엔 카드 안 다른 요소보다 넓은 간격(`Theme.Spacing.md`)을 줬다. "내 목소리로 화음" 카드는 설명 캡션을 버튼 위로 옮겼다 — 버튼을 누르기 전에 "이게 뭘 하는 버튼인지"부터 읽히도록.

## 34. 버튼에 아이콘 붙이기 — "상태를 의미하는" 곳에만

### 어디에 아이콘을 붙였고 어디는 안 붙였나

`Button("텍스트", action:)`을 `Button(action:) { Label("텍스트", systemImage: "...") }` 형태로 바꿔서, 측정 시작/중지, 시작음 듣기, 화음 듣기/정지, 전체 3도·5도 듣기/정지, 채점/중지, 다시 시작, 설정 열기, 내 목소리로 3도/5도/전체 화음 — 이렇게 주로 "지금 상태"(재생 중/정지, 켜짐/꺼짐)를 표현하거나 화면의 주요 동작인 버튼에 아이콘을 붙였다. 반대로 멜로디 스텝 줄의 "3도"/"5도" 같은 아주 짧은 라벨 버튼에는 일부러 아이콘을 안 붙였다 — 이미 공간이 좁은 곳에 억지로 넣을 의미 있는 아이콘이 마땅치 않았고(예: "3도"를 표현하는 아이콘이 따로 없음), 장식으로만 붙이는 아이콘은 오히려 화면을 산만하게 만든다.

### 상태에 따라 아이콘 자체가 바뀐다

"측정 시작"/"측정 중지"처럼 같은 버튼이 상태에 따라 텍스트가 바뀌는 곳은, 아이콘도 같이 바꿨다(`mic.fill` ↔ `stop.fill`, `play.fill` ↔ `stop.fill`). 텍스트만 바뀌는 것보다, 아이콘 모양 자체가 바뀌는 게 "지금 이 버튼을 누르면 정지시키는 동작이다"라는 걸 텍스트를 읽기 전에도 형태로 먼저 전달한다 — 재생/정지 버튼에서 흔히 쓰는 관례이기도 하다.

### 중복 코드를 계산 프로퍼티로 정리

`ViewThatFits`(32절)로 가로/세로 두 레이아웃에 같은 버튼을 두 번씩 넣다 보니, 아이콘까지 추가하면 같은 버튼 정의가 코드에 두 벌씩 반복될 뻔했다. 버튼 하나하나를 `private var voiceThirdButton: some View { ... }`처럼 계산 프로퍼티로 뽑아내서, `ViewThatFits`의 가로/세로 버전 양쪽에서 같은 프로퍼티를 참조하게 했다 — 아이콘/텍스트가 나중에 또 바뀌어도 한 곳만 고치면 된다.

## 35. 카드 등장 애니메이션 + 자동 스크롤

### 왜 필요했나

카드가 조건부로(점진적 공개, 23/29절) 나타나는 방식 자체는 유지하기로 했지만, 지금까지는 조건이 참이 되는 순간 카드가 **애니메이션 없이 툭 나타났다**. 사용자가 "화면을 단계별로 나누는 게 낫지 않냐"고 물어봤을 때, 화면을 실제로 나누는 대신(상태가 여러 카드에 걸쳐 얽혀 있어서 나누면 오히려 복잡해짐, 34절과 같은 판단) 가벼운 애니메이션과 자동 스크롤로 "새로 생겼다"는 걸 더 잘 느끼게 하기로 했다.

### `.transition` + `.animation(value:)` — 왜 둘 다 필요한가

SwiftUI에서 `if` 조건으로 뷰가 나타나거나 사라지는 걸 애니메이션으로 보여주려면 두 가지가 같이 있어야 한다:
- **`.transition(...)`**: 뷰가 나타날 때/사라질 때 "어떻게" 보일지(페이드, 이동 등)를 정의한다. 여기선 `.opacity.combined(with: .move(edge: .top))` — 투명도가 서서히 올라가면서 동시에 위에서 살짝 내려오듯 나타나게 했다.
- **`.animation(_:value:)`**: 그 전환을 "애니메이션으로 처리하라"고 SwiftUI에 알려준다. `.transition`만 있고 `.animation`이 없으면 조건이 바뀌는 순간 즉시(애니메이션 없이) 나타나거나 사라진다 — 실제로 처음엔 이걸 빠뜨려서 애니메이션이 전혀 안 먹는 걸 발견했다.

`melodySession.suggestedHarmony`는 `[HarmonyNote]?`라 `.animation(value:)`가 요구하는 `Equatable` 비교에 그대로 쓰기 애매해서, `hasHarmony`라는 단순 `Bool` 계산 프로퍼티로 한 번 감싸서 썼다.

### `ScrollViewReader`로 새로 나타난 카드까지 자동 스크롤

카드가 늘어나면서 화면이 길어지면, 방금 나타난 카드가 화면 밖(스크롤해야 보이는 위치)에 있을 수 있다. `ScrollViewReader`는 스크롤 가능한 컨텐츠 안의 뷰마다 `.id(...)`를 붙여두면, 그 id로 "이 위치로 스크롤해줘"라고 명령할 수 있는 `proxy`를 준다. `.onChange(of: hasCapturedNote)`/`.onChange(of: hasHarmony)`로 각각의 조건이 "처음으로 참이 되는 순간"을 감지해서, `proxy.scrollTo("keyHarmonyCard", anchor: .top)`처럼 방금 나타난 카드로 부드럽게 스크롤시킨다.

## 36. "빠른 녹음 → 악보 → 연습" 로드맵 착수 — `MelodySegmenter`(음표 분할)

### 왜 실시간 캡처와 다른 새 파이프라인이 필요한가

지금까지의 `MelodySession`은 마이크 프레임을 실시간으로 **하나씩** 받아서 "지금 이 음으로 확정할지"를 그 자리에서 판단하는 구조다. 새로 하려는 건 "일단 노래를 통째로 녹음한 뒤, 녹음 전체를 한 번에 훑어서 음표들로 잘라내는" 배치(batch) 방식이라 — `MelodySession`을 고쳐 쓰는 대신, 완전히 새로운 배치 전용 분석기 `MelodySegmenter`를 만들었다. `MelodySession`은 그대로 두고(단음/멜로디 실시간 모드가 계속 씀), `MelodySegmenter`가 그 옆에 새로 추가되는 형태다.

### 세 단계: 윈도우 분석 → 디바운스 → 런랭스 인코딩

1. **윈도우 분석**: 녹음 전체를 2048샘플짜리 윈도우로, 75% 겹치게(홉 512샘플) 훑으면서 윈도우마다 `VoiceActivityDetector`(무음 여부) + `YINPitchDetector`(피치) + `NoteNameConverter.exactMIDINote(...).rounded()`(반올림한 MIDI 노트)를 계산한다. 윈도우 크기(2048)는 새로 튜닝하지 않고 기존 `AudioCapture`가 이미 80Hz까지 검증해둔 값을 그대로 재사용했다 — 홉만 훨씬 촘촘하게(약 11.6ms) 잡아서, 실시간 파이프라인(프레임당 약 46ms)보다 "음이 정확히 언제 시작했는지"를 더 세밀하게 잡아낸다.
2. **디바운스**: 같은 MIDI 노트가 `streakRequired`(3)번 연속 나와야 "확정"되고, 그 전까지는 미확정(nil)으로 둔다. 이건 실시간 캡처의 `captureStreakRequired`(3프레임 연속 유지돼야 확정)와 정확히 같은 원리를 윈도우 단위로 옮긴 것 — 노이즈성 윈도우 한두 개 때문에 음이 잘못 잘리는 걸 막는다. 비브라토(반음 안에서 흔들리는 정도)는 반올림한 MIDI 노트 자체가 안 바뀌니 자동으로 한 음으로 유지된다.
3. **런랭스 인코딩**: 디바운스를 거친 시퀀스에서 같은 값이 이어지는 구간을 하나의 음표(`SegmentedNote`)로 묶고, `minimumNoteDuration`(0.08초)보다 짧은 구간은 버린다.

세 단계를 하나로 합치지 않고 나눈 이유는, "이 값이 확정됐는지 판단하는 로직"과 "확정된 값들을 구간으로 묶는 로직"을 따로 검증할 수 있게 하기 위해서다 — `PitchShifter`를 만들 때(20절) `timeStretch`/`resample`을 분리해서 버그를 이분 탐색하듯 찾았던 것과 같은 이유다.

### 테스트로 확인한 것과, 테스트를 만들며 발견한 함정

유닛테스트는 사인파를 이어붙여 만든 합성 버퍼로: 지속음 하나, 무음 없이 붙은 서로 다른 두 음, 무음으로 분리된 두 음, 최소 길이보다 짧은 blip, 비브라토가 있는 한 음 — 이렇게 다섯 가지를 확인한다. blip 테스트를 만들면서 함정을 하나 발견했다: 처음엔 blip 길이를 0.05초로 잡았는데, 이게 분석 윈도우 길이(2048샘플 ≈ 0.046초)보다 살짝 길어서, 윈도우 여러 개가 blip에 걸쳐 "스며들어" 실제보다 길게 잡히는 바람에 최소 길이 필터를 통과해버렸다 — 즉 "짧은 소리는 걸러진다"는 걸 제대로 검증하려면, blip이 분석 윈도우 자체보다 뚜렷이 짧아야 한다(0.02초로 줄여서 해결). 윈도우 기반 분석은 이렇게 "이벤트가 윈도우보다 짧을 때 실제보다 길게 관측될 수 있다"는 특성이 있다는 걸 테스트를 짜면서 직접 확인한 셈이다.

### 아직 잠정값인 것들

`windowSize`/`hop`/`streakRequired`/`minimumNoteDuration`은 전부 합성 사인파 기준으로 논리를 검증한 값이지, 실제 목소리(숨소리, 콧소리, 음 사이 글라이드, 자음 시작 잡음)로 튜닝된 값이 아니다. 다음 단계(빠른 녹음 UI + 실기기)에서 실제로 불러보고 다시 조정할 예정이다.
